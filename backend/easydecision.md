# T0. 함께 일하는 규칙

## T0-01. 이름 짓기 규칙과 자동 검사 범위

### 현재 상황

[코드에서 확인] `CONTRIBUTING.md`에는 브랜치, 커밋, PR, 리뷰 규칙이 있지만 "변수/클래스/파일/DB 필드 이름은 어떻게 짓는다"라는 통일 표는 없습니다. 실제 코드는 여러 스타일이 섞여 쓰이고 있습니다.

[미결정] 새 코드를 만들 때 어떤 이름 규칙을 따를지, 자동 검사(린트/CI)가 어디까지 검사할지 정해지지 않았습니다.

### 왜 결정이 필요한가

이름이 제각각이면 같은 뜻을 여러 번 만들거나, 앱과 DB 필드 이름이 달라 매칭을 틀리기 쉽습니다. 이 프로젝트는 앱↔서버↔DB 사이 이름이 조금씩 달라 사람이 손으로 매핑하므로 기준이 없으면 약속을 놓치기 쉽습니다.

### 선택 가능한 옵션

- 옵션 A: 팀 판단에 맡긴다
  - 장점: 새 문서와 도구를 만들지 않아도 됩니다.
  - 단점: 모듈마다 이름과 파일 구조가 달라져 리뷰 비용이 커집니다.

- 옵션 B: 공통 이름 표와 자동 검사 규칙을 확정한다
  - 장점: 새 코드가 어떤 형태일지 예측 가능하고 기계로 검사할 수 있습니다.
  - 단점: 기존 예외 이름을 정리할 때 작은 수정이 필요합니다.

### 추천안

옵션 B. 클래스/DTO/enum은 파스칼케이스, 변수/함수/응답은 카멜케이스, 파일명은 케밥케이스, DB 필드는 스네이크케이스, 환경변수는 대문자 스네이크케이스로 씁니다. 외부 API 원본 필드명은 클라이언트 안에서만 쓰고 서비스 밖으로 꺼내지 않습니다.

### 추천 이유

지금 코드와 가장 잘 맞고, 앱/DB/외부 API 경계를 이름만 보고 구분할 수 있습니다. 새 규칙은 린트와 PR 리뷰에서 자동·수동으로 같이 확인할 수 있습니다.

### 영향 범위

- `backend/src/**`
- `backend/prisma/schema.prisma`
- `backend/.env.example`
- `src/types/**`, `src/api/**`, ESLint 및 PR 리뷰 기준

# T1. NestJS 기본 구조와 공통 API

## T1-01. NestJS와 낡은 FastAPI 중 어떤 것을 운영할지

### 현재 상황

[코드에서 확인] 지금 운영 기준은 NestJS + TypeScript + Prisma + PostgreSQL + Redis입니다. 동시에 `backend/app/`에 옛날 Python(FastAPI) 코드가 남아 있고 CI도 Python 문법 검사를 합니다. README는 Python을 "참고용·점진 이식"이라고 적지만 실제 사용자 요청을 어느 쪽이 받는지는 명시되어 있지 않습니다.

[미결정] NestJS를 운영 유일 기준으로 확정할지, FastAPI를 언제 읽기 전용/참고용으로 전환하고 삭제할지 정해지지 않았습니다.

### 왜 결정이 필요한가

두 구현을 동시에 두면 인증·날씨·추천·오류 응답·DB 접근 방식이 또 갈라질 수 있습니다. 장애가 났을 때 어느 코드가 기준인지도 모호해집니다.

### 선택 가능한 옵션

- 옵션 A: NestJS와 FastAPI를 장기 같이 운영한다
  - 장점: 기존 Python 기능을 당장 폐기하지 않아도 됩니다.
  - 단점: API·보안·마이그레이션·운영 비용을 두 번 관리해야 합니다.

- 옵션 B: NestJS를 기준으로 확정하고 FastAPI에 종료 조건을 둔다
  - 장점: 인증·DB·오류·배포 기준을 하나로 유지할 수 있습니다.
  - 단점: FastAPI 사용자 동등성 검증과 트래픽 전환 계획이 필요합니다.

### 추천안

옵션 B. NestJS를 운영 API의 단일 기준으로 삼고, FastAPI는 실제 트래픽이 없는 참고·이식 검증용으로만 남깁니다. NestJS의 API 계약·e2e 검증이 끝나고 사용자 전환이 확인되면 FastAPI 라우터와 전용 DB 코드를 제거합니다.

### 추천 이유

지금 T0~T14 최종 구조와 CI는 NestJS 기준으로 만들어져 있습니다. 두 구현을 운영에 두는 건 점진 전환엔 도움되지만 최종 구조로는 일관성이 떨어집니다.

### 영향 범위

- `backend/app/**`
- `backend/src/**`
- `.github/workflows/ci.yml`
- `backend/README.md`, 배포·트래픽 전환 설정

## T1-02. 모듈 나누는 기준과 저장소(Repository) 도입 시점

### 현재 상황

[코드에서 확인] Auth, Weather, Diagnosis, Recommendation, Product, Pattern, Notification, Gemini, Health가 모듈로 나뉘어 있습니다. Controller는 HTTP 처리, Service는 비즈니스 로직을 담당하고 외부 API는 Client, 계산 규칙은 Policy로 뺐습니다. 단순 CRUD는 Service가 Prisma를 직접 호출하고 PrismaModule은 전역입니다.

[미결정] 모듈을 언제 나누고, 얼마나 복잡해질 때 Repository나 별도 정책(Policy) 객체를 도입할지 명시되어 있지 않습니다.

### 왜 결정이 필요한가

무조건 Repository를 만들면 껍데기만 늘고, 반대로 Service가 모든 SQL·매핑·정책을 가지면 책임이 너무 커집니다. 모듈끼리 직접 Service를 부르면 순환 참조도 생길 수 있습니다.

### 선택 가능한 옵션

- 옵션 A: 모든 모듈에 Controller-Service-Repository-DTO를 강제한다
  - 장점: 구조가 형식적으로 통일됩니다.
  - 단점: 단순 조회에도 파일과 추상화가 늘어납니다.

- 옵션 B: 책임과 복잡도 기준으로 필요할 때만 도입한다
  - 장점: 현재 규모에서 불필요한 추상화를 피하면서 복잡한 쿼리·트랜잭션은 따로 묶을 수 있습니다.
  - 단점: 도입 기준을 리뷰어가 계속 판단해야 합니다.

### 추천안

옵션 B. 모듈은 사용자에게 제공하는 도메인 책임 기준으로 나눕니다. 하나의 Service가 여러 데이터 덩어리를 조합하거나 복잡한 SQL·잠금·페이지네이션·재사용 쿼리를 가지면 Repository/Query 객체를 도입합니다. 모듈 간에는 공개된 Service interface만 쓰고 다른 모듈의 Prisma 모델을 직접 조회하지 않습니다.

### 추천 이유

`BACKEND_TASKS.md`의 "단순 CRUD마다 Repository를 무조건 만들지 않는다"는 방향을 유지하면서, 규모가 커질 때 Service가 비대해지는 걸 막습니다.

### 영향 범위

- `backend/src/modules/**`
- `backend/src/prisma/**`
- Prisma 쿼리, 트랜잭션, 모듈 import/export 구조

## T1-03. 전역 공통 모듈 사용 기준

### 현재 상황

[코드에서 확인] `PrismaModule`과 `RedisModule`은 `@Global()`이라 모든 모듈에서 Service를 바로 주입할 수 있습니다. 날씨 외에도 향후 Redis를 쓸 수 있지만 지금은 날씨 캐시가 주 사용처입니다.

[미결정] 전역 모듈에 어떤 인프라를 추가할 수 있고, 어떤 기능은 모듈에서 명시적으로 import해야 하는지 기준이 없습니다.

### 왜 결정이 필요한가

전역 의존성은 편하지만 어떤 모듈이 DB·Redis·외부 서비스를 쓰는지 import만 보면 알기 어렵게 만듭니다. 테스트에서도 숨은 전역 상태가 생길 수 있습니다.

### 선택 가능한 옵션

- 옵션 A: 모든 공통 인프라를 전역으로 제공한다
  - 장점: 모듈 설정과 import가 간단합니다.
  - 단점: 의존성이 숨고 테스트 격리가 어렵습니다.

- 옵션 B: Prisma만 전역으로 두고 기능별 인프라는 명시적으로 import한다
  - 장점: 모듈 관계와 기능 사용 범위가 명확합니다.
  - 단점: import/export 설정이 늘어납니다.

### 추천안

옵션 B. Prisma는 앱 공통 저장소라 전역을 유지하고, Redis·Queue·외부 클라이언트 묶음은 쓰는 도메인 모듈이 명시적으로 import합니다. 전역 Service는 요청 상태나 사용자 상태를 가지지 않습니다.

### 추천 이유

지금 Redis는 선택적 성능 계층이라 모든 모듈에 숨겨진 의존성을 줄 필요가 없습니다. AI Queue가 나중에 추가돼도 사용 모듈을 명확히 제한할 수 있습니다.

### 영향 범위

- `backend/src/prisma/prisma.module.ts`
- `backend/src/redis/redis.module.ts`
- `backend/src/app.module.ts`
- `backend/src/modules/**`

## T1-04. API 버전 관리와 낡은 약속 종료

### 현재 상황

[코드에서 확인] API에는 `/v1` 같은 버전 표시가 없습니다. 옛날 FastAPI 호환을 위해 `/auth/login` 응답은 사용자 필드와 토큰을 같이 주고, 추천 생성은 `diagnosisId`와 옛날 방식 `skinScore+weather` 둘 다 받습니다.

[미결정] 호환성을 깰 때 버전을 붙일지, 옛날 약속을 언제 없앨지 정해지지 않았습니다.

### 왜 결정이 필요한가

호환 때문에 옛날 형식을 계속 허용하면 서버가 옛날 입력을 영원히 지원하게 됩니다. 반대로 예고 없이 없애면 앱 업데이트가 늦어 장애가 납니다.

### 선택 가능한 옵션

- 옵션 A: URL 버전 없이 모든 변경을 하위 호환으로 처리한다
  - 장점: URL과 클라이언트 변경이 최소화됩니다.
  - 단점: DTO와 분기 로직이 계속 쌓입니다.

- 옵션 B: 지금 약속은 유지하다가 호환성을 깰 때부터 `/v1`과 폐기 기간을 적용한다
  - 장점: 약속의 수명과 제거 시점을 관리할 수 있습니다.
  - 단점: 잠시 두 API 버전을 운영해야 합니다.

### 추천안

옵션 B. 지금 경로는 호환 기간 동안 유지하되 새로 호환성을 깨는 API는 `/v1`을 씁니다. `POST /recommendations/generate`는 `diagnosisId` 전용으로 전환할 날짜와 앱 최소 버전을 정하고, 옛날 입력은 경고 로그·지표 후 제거합니다.

### 추천 이유

지금 프런트가 `diagnosisId`를 보내는 코드와 옛날 호환 분기를 같이 가지고 있어 즉시 제거보다 명시적 전환 기간이 안전합니다.

### 영향 범위

- `backend/src/main.ts`
- `backend/src/modules/recommendations/**`
- `backend/src/modules/auth/**`
- `src/api/client.ts`, 모바일 앱 배포·릴리스 정책

## T1-05. 성공 응답 형태와 null/빈 배열/404 기준

### 현재 상황

[코드에서 확인] 성공 응답은 대부분 배열이나 DTO를 그대로 줍니다. 데이터가 없을 때 진단 최신과 추천 상세는 404, 알림 설정은 기본값을 200으로 주고, Pattern은 404 대신 200 + `LOCKED`를 줍니다. 선택 지표는 `null`, 관련 제품 ID는 빈 배열입니다.

[미결정] 도메인별로 없음/빈 목록/측정 불가를 404·200 빈 배열·`null`·명시적 상태 중 어떤 걸로 표현할지, 공통 응답 포맷을 도입할지 정해지지 않았습니다.

### 왜 결정이 필요한가

프런트가 "자료 없음", "아직 준비 안 됨", "측정 불가", "정상 빈 목록"을 구분해야 합니다. 표현이 섞이면 화면 상태와 재시도 정책이 틀립니다.

### 선택 가능한 옵션

- 옵션 A: 지금 도메인별 그대로 응답을 유지한다
  - 장점: 기존 프런트 약속을 유지합니다.
  - 단점: 새 API마다 응답 의미를 따로 문서화해야 합니다.

- 옵션 B: 공통 응답 포맷과 상태 표현을 도입한다
  - 장점: 응답 구조와 상태 처리가 통일됩니다.
  - 단점: 모든 프런트 파서와 기존 약속을 바꿔야 합니다.

### 추천안

옵션 A를 당장 유지하되 규칙을 문서화합니다. 단일 자료의 없음은 404, 정상 빈 목록은 200 + `[]`, 측정·수집 불가는 해당 값 `null`과 source/status, 분석 데이터 부족은 200 + 도메인 상태(`LOCKED`)로 표현합니다. 공통 응답 포맷은 다음 major API 버전에서만 검토합니다.

### 추천 이유

지금 프런트가 배열과 DTO를 그대로 쓰므로 약속을 지키면서 의미만 고정하는 게 가장 안전합니다.

### 영향 범위

- 모든 `backend/src/modules/**/dto/**`
- `backend/src/common/exceptions/**`
- `src/api/client.ts`, 화면별 로딩/빈/에러 처리

## T1-06. 에러 응답과 커스텀 예외 사용 기준

### 현재 상황

[코드에서 확인] 전역 예외 필터가 Nest 예외와 Prisma 오류(P2002/P2025/P2003), 파일 업로드 오류를 공통 형태로 변환합니다. 모르는 500 오류 내부 메시지는 숨깁니다. 도메인별 커스텀 예외 계층과 안정적인 에러 코드는 없습니다.

[미결정] 언제 Nest 기본 예외를 쓰고 언제 도메인 예외·에러 코드를 만들지 정해지지 않았습니다.

### 왜 결정이 필요한가

문자열 메시지를 약속으로 쓰면 문구 바꿈이 클라이언트 로직을 깹니다. 예외가 Service마다 다르면 "다시 시도 가능한 오류"와 "사용자 입력 오류"를 구분하기 어렵습니다.

### 선택 가능한 옵션

- 옵션 A: Nest 기본 예외과 문자열 메시지를 계속 쓴다
  - 장점: 구현이 단순합니다.
  - 단점: 안정적인 기계 판별 값이 없습니다.

- 옵션 B: 공통 커스텀 예외과 안정적인 에러 코드를 도입한다
  - 장점: `AUTH_INVALID_TOKEN`, `RESOURCE_NOT_FOUND`, `AI_UNAVAILABLE` 같은 정해진 코드로 클라이언트가 한국어 메시지를 파싱하지 않아도 되고 로그·지표에서 오류 유형별 빈도를 집계할 수 있습니다.
  - 단점: 에러 코드 목록을 버전 관리하고 모든 Service에서 같은 코드를 쓰도록 매핑 표를 유지해야 하며, 새 코드 추가 시 클라이언트 최소 버전 호환성을 고려해야 합니다.

### 추천안

옵션 B. HTTP 상태는 지금 약속을 유지하고 `AUTH_INVALID_TOKEN`, `RESOURCE_NOT_FOUND`, `AI_UNAVAILABLE`, `WEATHER_UNAVAILABLE`, `VALIDATION_FAILED` 같은 내부 에러 코드를 추가합니다. 단순 입력 오류는 Nest 기본 예외를 허용하되 반복되거나 재시도·화면 분기가 필요한 도메인 오류는 커스텀 예외를 씁니다.

### 추천 이유

지금 `detail` 호환을 유지하면서도 나중에 프런트가 한국어 메시지를 파싱하지 않게 할 수 있습니다.

### 영향 범위

- `backend/src/common/filters/http-exception.filter.ts`
- `backend/src/common/exceptions/**`
- 모든 Service, Swagger와 `src/api/client.ts`

# T2. PostgreSQL, Prisma 그리고 데이터 모델

## T2-01. 옛날 SQLite 데이터 옮기기와 데이터 소유권

### 현재 상황

[코드에서 확인] `backend/app/`에는 옛날 SQLite/SQLAlchemy 모델이 남아 있고 새 운영 스키마는 PostgreSQL + Prisma 마이그레이션을 씁니다. `BACKEND_TASKS.md`는 기존 사용자·추천·진단을 단순 복사가 아닌 정리 대상이라고 하지만 실제 데이터 옮기기 절차는 없습니다.

[미결정] SQLite를 실제로 옮길지, 초기 사용자·추천·진단의 보존·중복·누락을 어떻게 처리할지 확정되지 않았습니다.

### 왜 결정이 필요한가

데이터를 잘못 합치면 진단과 추천의 소유권이나 근거 연결이 깨질 수 있습니다. 액세스 토큰을 안 옮기고 다시 로그인시키는 정책도 실제 단계에서 명시되어야 합니다.

### 선택 가능한 옵션

- 옵션 A: 운영 전환 시 새 PostgreSQL을 빈 DB로 시작한다
  - 장점: 옮기기 도구와 데이터 정합성 검증이 필요 없습니다.
  - 단점: 기존 사용자와 진단 이력을 잃습니다.

- 옵션 B: 검증된 일회성 옮기기를 수행한다
  - 장점: 사용자 데이터와 이력을 보존할 수 있습니다.
  - 단점: 필드 매핑, 중복 제거, 롤백·백업 절차가 필요합니다.

### 추천안

옵션 B. 원본 SQLite 백업을 보존하고 staging에서 옮기를 검증한 뒤 User·Diagnosis·SkinMetric·Recommendation 매핑 보고서를 만듭니다. 성별은 기존 데이터에 `null`, 액세스 토큰은 옮기지 않고 전원 재로그인, 중복 추천은 diagnosisId와 생성시각 기준으로 정리합니다. 옮기기는 운영 트래픽과 분리된 일회성 명령으로 실행하고 건수·체크섬을 확인합니다.

### 추천 이유

기존 서비스 사용자 경험을 보존하면서도 토큰과 민감정보를 그대로 옮기지 않을 수 있습니다.

### 영향 범위

- `backend/app/models.py`, `backend/app/database.py`
- `backend/prisma/schema.prisma`, `backend/prisma/seed.ts`
- 옮기기 스크립트, 백업, 운영 전환 runbook

## T2-02. ID 생성과 외부 공개 식별자 규칙

### 현재 상황

[코드에서 확인] User·일부 조인 모델은 자동증가 정수이고 Diagnosis·WeatherSnapshot·Recommendation·RefreshSession은 UUID 또는 UUID 파생 문자열을 씁니다. 일부 추천 ID는 `gemini-` 접두사를 붙인 임의 UUID 파생값입니다.

[미결정] 내부 DB ID와 API 공개 ID를 같은 값으로 쓸지, 모델별 ID 규칙을 통일할지 정해지지 않았습니다.

### 왜 결정이 필요한가

숫자 ID를 외부에 노출하면 자원을 추측해서 열거할 위험이 있고, 접두사 규칙이 모듈마다 다르면 추적·이식이 어렵습니다.

### 선택 가능한 옵션

- 옵션 A: 현재 모델별 ID 방식을 유지한다
  - 장점: 마이그레이션이 없습니다.
  - 단점: 규칙이 복잡하고 공개 ID 보호가 각 API에 의존합니다.

- 옵션 B: 내부 키와 공개 식별자를 분리한다
  - 장점: 외부 노출·이식·분산 생성 정책을 독립적으로 관리할 수 있습니다.
  - 단점: 컬럼과 매핑이 추가됩니다.

### 추천안

옵션 B를 새 외부 자원부터 적용합니다. User 내부 ID는 정수로 유지하되 API에는 외부에서 알 수 없는 공개 ID를 쓰고, Diagnosis·Recommendation·WeatherSnapshot은 UUID 계열 공개 ID를 유지합니다. 생성 주체를 구분하는 접두사는 표시용으로만 쓰고 식별자 의미로 의존하지 않습니다.

### 추천 이유

기존 DB를 크게 바꾸지 않으면서 사용자 ID 열거를 줄이고, 분산·비동기 생성으로 확장하기 쉽습니다.

### 영향 범위

- `backend/prisma/schema.prisma`
- Auth/User 및 모든 `:id` Controller
- `src/types/**`, 마이그레이션·seed·로그 연결 필드

## T2-03. 삭제, 소프트 삭제와 보존 기간

### 현재 상황

[코드에서 확인] 소프트 삭제 필드는 없고 User 삭제 시 RefreshSession·Diagnosis·Recommendation·ConsentRecord·NotificationPreference가 같이 삭제(Cascade)됩니다. Diagnosis에서 Recommendation은 참조를 끊고(SetNull), RecommendationProduct는 양쪽에서 삭제됩니다. 원본 이미지는 저장하지 않습니다.

[미결정] 회원 탈퇴·개인정보 삭제·법적 보존·분석 데이터 보존을 물리 삭제와 소프트 삭제 중 어떤 방식으로 처리할지 결정되지 않았습니다.

### 왜 결정이 필요한가

Cascade는 간단하지만 탈퇴 후 복구·감사·법정 보존을 어렵게 합니다. 소프트 삭제를 도입하고 조회 조건을 빠뜨리면 삭제된 데이터가 사용자에게 보일 수 있습니다.

### 선택 가능한 옵션

- 옵션 A: 물리 삭제와 Cascade를 기본으로 한다
  - 장점: 개인정보 제거가 명확하고 조회가 단순합니다.
  - 단점: 감사·분쟁 대응과 통계 재현이 어렵습니다.

- 옵션 B: 사용자·진단 등 일부 데이터에 소프트 삭제와 보존 기간을 둔다
  - 장점: 유예 기간·감사·복구가 가능합니다.
  - 단점: 모든 쿼리에 삭제 조건과 최종 정리 작업이 필요합니다.

### 추천안

개인정보와 원본 이미지는 물리 삭제를 기본으로 하고, 법적·운영적으로 보존이 필요한 진단 결과만 별도 익명화 후 보존합니다. 소프트 삭제를 User/Diagnosis에 도입할 경우 공통 repository/query 정책과 최종 정리 기한을 함께 만듭니다. 모든 외래키의 Cascade/SetNull/Restrict 정책을 모델별 표로 확정합니다.

### 추천 이유

지금 원본 이미지를 저장하지 않는 원칙과 충돌하지 않으면서 탈퇴와 데이터 재현 요구를 분리할 수 있습니다.

### 영향 범위

- `backend/prisma/schema.prisma`, 모든 마이그레이션
- Auth 탈퇴, Diagnosis/Recommendation 조회·삭제
- ConsentRecord, 정리 job, 개인정보 처리방침

## T2-04. 시간대와 날짜 필드 규칙

### 현재 상황

[코드에서 확인] Prisma DateTime은 UTC 기준으로 저장하고 API는 ISO 문자열로 줍니다. 생년월일은 UTC 자정으로 파싱하고, KMA·AirKorea의 KST 시각을 UTC로 변환합니다. Pattern은 capturedAt을 날짜 단위로 잘라 서로 다른 날짜 수를 계산합니다.

[미결정] 사용자 날짜와 관측·수집 시각의 기준 시간대, 날짜 경계, 서머타임·서버 시간 동기화 정책이 문서화되어 있지 않습니다.

### 왜 결정이 필요한가

한국 날짜와 UTC 날짜가 자정에 달라지면 생년월일·진단 이력·패턴 수집일이 다르게 계산될 수 있습니다. 외부 API 관측 시각과 서버 수집 시각을 혼동하면 재현성이 떨어집니다.

### 선택 가능한 옵션

- 옵션 A: 모든 날짜를 서버 UTC 기준으로 계산한다
  - 장점: 분산 서버에서 일관됩니다.
  - 단점: 한국 사용자에게 날짜가 직관적이지 않습니다.

- 옵션 B: 저장·전송은 UTC, 사용자·도메인 날짜 계산은 서비스 기준 시간대(지금 KST)로 한다
  - 장점: 저장 표준과 사용자 의미를 모두 보존합니다.
  - 단점: 날짜 계산 헬퍼와 테스트가 필요합니다.

### 추천안

옵션 B. 시점은 UTC로 저장·전송하고, 생년월일과 패턴의 서로 다른 날짜는 `Asia/Seoul` 기준으로 계산합니다. 외부 관측 시각은 원문 시간대 변환 후 `observedAt`, 서버 수집 시각은 `collectedAt`으로 분리합니다.

### 추천 이유

지금 외부 API가 KST를 쓰고 사용자가 한국인이라는 구현 사실을 유지하면서 DB와 API의 시간 표현은 표준화할 수 있습니다.

### 영향 범위

- `backend/src/modules/auth/auth.service.ts`
- `backend/src/modules/weather/clients/**`
- `backend/src/modules/pattern/pattern.service.ts`
- Prisma DateTime 필드, 테스트 fixture와 운영 서버 시간 동기화

## T2-05. 트랜잭션·잠금·멱원성 적용 기준

### 현재 상황

[코드에서 확인] Diagnosis + SkinMetric, Recommendation 생성은 트랜잭션을 씁니다. 진단 중복 제출·WeatherSnapshot 중복 제거·Recommendation 중복 생성에 PostgreSQL 잠금(advisory lock)을 쓰고, 진단은 최근 60초 중복을 거부합니다. 외부 Gemini 호출은 트랜잭션/잠금 전에 수행합니다. WeatherSnapshot 중복 제거 조건은 지역·측정소·관측 분이지만 DB에 그 조합을 강제하는 유니크 제약은 없습니다.

[미결정] 어떤 요청을 "같은 요청 다시 보내도 같은 결과"로 볼지, 잠금 키와 트랜잭션 범위, 외부 호출과 저장 순서를 어떻게 유지할지 기준이 없습니다.

### 왜 결정이 필요한가

재시도·동시 요청이 늘면 진단·추천·스냅샷이 중복되거나 AI 호출 비용이 중복됩니다. 트랜잭션 안에 느린 외부 호출을 넣으면 잠금이 길어지고, 밖에 두면 중복 호출이 생깁니다.

### 선택 가능한 옵션

- 옵션 A: 지금처럼 도메인별 시간 창과 잠금을 조합한다
  - 장점: 마이그레이션이 작고 지금 기능을 유지합니다.
  - 단점: 잠금 키·중복 정책을 각 Service가 따로 관리합니다.

- 옵션 B: API 멱원성 키와 DB 유니크/비즈니스 키를 표준화한다
  - 장점: 재시도와 동시 요청의 결과를 명확히 재사용할 수 있습니다.
  - 단점: 키 저장·만료·응답 재생 정책이 필요합니다.

### 추천안

옵션 B를 외부 호출·비용이 큰 생성 API부터 적용합니다. 클라이언트 멱원성 키와 사용자·도메인 범위를 저장하고, DB 유니크 키는 가능한 중복 제거 기준에 추가합니다. 외부 호출은 잠금 밖에서 수행하되 키 기준 상태를 `PROCESSING/COMPLETED/FAILED`로 관리하고, 재시도 시 같은 결과를 돌려줍니다.

### 추천 이유

긴 외부 호출을 DB 잠금 안에 넣지 않으면서도 중복 비용과 부분 결과를 통제할 수 있습니다.

### 영향 범위

- `backend/src/modules/diagnosis/diagnosis.service.ts`
- `backend/src/modules/recommendations/recommendation.service.ts`
- `backend/src/modules/weather/weather.service.ts`
- Prisma 유니크/인덱스, API DTO와 트랜잭션 정책

## T2-06. 인덱스와 대량 조회·페이지네이션 기준

### 현재 상황

[코드에서 확인] User phone, Diagnosis(userId,capturedAt), WeatherSnapshot(regionName,observedAt), Recommendation(userId,diagnosisId,createdAt) 등의 인덱스가 있습니다. 진단 이력, 제품 목록, 추천 목록, 패턴 분석은 전체 행을 한 번에 읽고 페이지네이션·제한·커서가 없습니다. Pattern은 사용자 진단과 날씨 스냅샷을 메모리에 올립니다.

### 왜 결정이 필요한가

사용자 이력과 전체 카탈로그가 커지면 응답·메모리·DB 부하가 비례해서 커집니다. 인덱스가 실제 검색/정렬 조건과 다르면 비용만 늘립니다.

### 선택 가능한 옵션

- 옵션 A: 지금 전체 조회를 유지한다
  - 장점: API 약속과 구현이 단순합니다.
  - 단점: 데이터 증가에 취약합니다.

- 옵션 B: 목록은 커서 페이지네이션, 분석은 기간·샘플 상한과 집계 쿼리를 쓴다
  - 장점: 응답 크기와 메모리를 제한할 수 있습니다.
  - 단점: 클라이언트와 쿼리 설계가 바뀝니다.

### 추천안

옵션 B. 진단·추천·제품 목록은 기본/최대 limit를 문서화하고 커서 페이지네이션을 적용합니다. Pattern은 최근 기간 또는 최대 샘플 수를 정하고, 실행 계획과 실제 데이터 분포를 기준으로 복합 인덱스를 검토합니다. 날씨 중복 제거 쿼리와 RecommendationProduct 조회 인덱스를 별도로 점검합니다.

### 추천 이유

지금 API 약속을 유지하면서도 페이지네이션을 선택적으로 추가할 수 있고, Pattern의 메모리 적재 위험을 줄일 수 있습니다.

### 영향 범위

# T3. JWT 인증과 USER/ADMIN 권한

## T3-01. JWT 수명·전송·리프레시 토큰 저장 정책

### 현재 상황

[코드에서 확인] 액세스 토큰 기본 만료는 15분, 리프레시 토큰 기본 만료는 14일입니다. 리프레시 토큰은 응답 본문으로 받고 DB에는 SHA-256 해시를 저장하며, 갱신 시 기존 세션을 폐기합니다. 앱은 AsyncStorage에 액세스 토큰 중심으로 세션을 저장하고 자동 갱신은 구현되어 있지 않습니다.

[미결정] 운영 최대 수명, 리프레시 전송 방식(본문·HttpOnly 쿠키), 모바일 저장소, 탈취·재사용 대응 기준이 완전히 확정되지 않았습니다.

### 왜 결정이 필요한가

토큰은 계정 접근의 핵심 자격증명입니다. 응답 본문과 일반 저장소에 장기 토큰을 남기면 로그·백업·악성 앱 노출 위험이 있습니다.

### 선택 가능한 옵션

- 옵션 A: 지금 본문 + AsyncStorage + 15분/14일 정책을 유지한다
  - 장점: 지금 프런트와 호환됩니다.
  - 단점: 리프레시 토큰 보호와 자동 갱신이 약합니다.

- 옵션 B: 모바일 보안 저장소와 갱신/재사용 탐지를 표준으로 한다
  - 장점: 토큰 탈취 대응력이 높습니다.
  - 단점: 앱 변경과 세션 재발급 UX가 필요합니다.

### 추천안

옵션 B. 액세스 토큰은 Bearer 헤더로 유지하고, 리프레시 토큰은 모바일 보안 저장소에만 저장합니다. 웹을 추가할 때는 HttpOnly·Secure·SameSite 쿠키를 별도 정책으로 둡니다. 액세스 15분, 리프레시 14일은 초기 기본값으로 유지하되 환경별 최대값을 검증합니다. 갱신 실패·재사용 탐지 시 해당 세션 또는 사용자 세션을 폐기하고 401을 반환합니다.

### 추천 이유

기존 API 약속을 크게 바꾸지 않으면서 장기 토큰의 보호와 재사용 대응을 강화할 수 있습니다.

### 영향 범위

- `backend/src/modules/auth/**`
- `backend/src/common/strategies/jwt.strategy.ts`
- `src/lib/session.ts`, `src/api/client.ts`
- 모바일 보안 저장소와 인증 e2e

## T3-02. 로그아웃 범위와 세션 관리

### 현재 상황

[코드에서 확인] `POST /auth/logout`은 현재 사용자의 폐기되지 않은 모든 RefreshSession을 폐기합니다. Service 주석에는 나중에 userAgent/ipAddress로 기기별 범위를 좁힐 수 있다고 적혀 있지만 기기 ID나 세션 목록 API는 없습니다.

[미결정] 기본 로그아웃이 현재 기기만인지 모든 기기인지, 세션 관리 화면을 제공할지 정해지지 않았습니다.

### 왜 결정이 필요한가

모든 세션 폐기는 보안상 안전하지만 사용자가 다른 기기에서 갑자기 로그아웃됩니다. 반대로 현재 기기만 폐기하면 분실 기기 대응 기능이 필요합니다.

### 선택 가능한 옵션

- 옵션 A: 모든 세션을 폐기한다
  - 장점: 로그아웃 효과가 명확하고 단순합니다.
  - 단점: 다른 기기의 정상 세션을 불필요하게 끊습니다.

- 옵션 B: 현재 세션 폐기와 전체 세션 폐기를 분리한다
  - 장점: UX와 보안을 모두 선택할 수 있습니다.
  - 단점: 세션 식별자와 세션 관리 API가 필요합니다.

### 추천안

옵션 B. RefreshSession에 외부에 공개하지 않는 세션 식별자를 연결하고, 기본 로그아웃은 현재 세션, `logout-all`은 전체 세션으로 분리합니다. 의심스러운 토큰 재사용이나 비밀번호·OTP 변경 시에는 전체 세션을 폐기합니다.

### 추천 이유

지금 DB에 userAgent·ipAddress·세션 ID가 이미 있어 점진적으로 구현할 수 있습니다.

### 영향 범위

- `backend/prisma/schema.prisma`
- `backend/src/modules/auth/auth.service.ts`
- Auth Controller/DTO, 모바일 계정 설정 화면

## T3-03. JWT 비밀키 교체와 리프레시 해시 보호

### 현재 상황

[코드에서 확인] 액세스/리프레시 비밀키는 서로 다른 환경변수이며 테스트 외 환경에서 32자 이상을 요구합니다. 리프레시 토큰 해시는 salt·pepper 없이 SHA-256으로 만듭니다. JWT 페이로드에는 `sub`, `role`, `jti`가 들어가지만 키 버전은 없습니다.

[미결정] 비밀키 교체 절차, 여러 키 검증 유예, 해시 pepper 관리, 유출 시 전체 세션 폐기 기준이 없습니다.

### 왜 결정이 필요한가

비밀키를 바꿀 때 기존 액세스 토큰을 즉시 다 무효화할지, 리프레시 토큰을 얼마나 인정할지 결정하지 않으면 배포 중 로그인 장애나 보안 공백이 생깁니다.

### 선택 가능한 옵션

- 옵션 A: 비밀키를 환경변수로 바꾸고 모든 토큰을 즉시 무효화한다
  - 장점: 절차가 단순하고 유출 대응이 빠릅니다.
  - 단점: 정상 사용자도 동시에 다시 로그인해야 합니다.

- 옵션 B: 키 ID와 이전 키 검증 유예를 둔다
  - 장점: 무중단 교체가 가능합니다.
  - 단점: 키 보관·만료·폐기 절차가 복잡합니다.

### 추천안

옵션 B. JWT 헤더의 `kid`와 활성/이전 키 목록을 Secret Manager에서 관리하고, 이전 키는 짧은 유예 기간만 검증합니다. 리프레시 해시는 서버 pepper를 추가한 HMAC-SHA-256으로 새로 저장하며, 비밀키 유출·대규모 이상 징후에는 전체 RefreshSession 폐기를 수행합니다.

### 추천 이유

운영 무중단과 긴급 폐기를 동시에 지원하면서 DB에 토큰 평문을 저장하지 않는 지금 방향을 유지할 수 있습니다.

### 영향 범위

- `backend/src/modules/auth/auth.service.ts`
- `backend/src/common/strategies/jwt.strategy.ts`
- `backend/src/config/env.validation.ts`
- Secret Manager, RefreshSession 마이그레이션과 운영 runbook

## T3-04. 전화번호 로그인에서 OTP·본인확인 도입 기준

[코드에서 확인] 회원가입과 로그인 모두 전화번호만 검증하며 비밀번호·OTP·SMS 발송이 없습니다. Controller Swagger에도 "비밀번호 없음 — MVP"라고 적혀 있습니다.

### 왜 결정이 필요한가

  - 장점: 전화번호 소유권을 확인할 수 있습니다.
  - 단점: SMS 제공자, 재전송 제한, 비용과 개인정보 정책이 필요합니다.

### 추천 이유

## T3-05. 역할 기반 권한과 퍼미션 도입 기준

### 현재 상황

[코드에서 확인] Role enum은 `USER`, `ADMIN` 두 값이고 `RolesGuard`가 `@Roles()` 메타데이터를 검사합니다. 실제 `@Roles(Role.ADMIN)` 라우트는 없습니다. 퍼미션 테이블·범위·자원 행위 모델도 없습니다.

[미결정] ADMIN 기능을 계속 역할 하나로 관리할지, 운영 기능이 늘면 퍼미션/스코프로 세분화할지 결정되지 않았습니다.

### 왜 결정이 필요한가

ADMIN에게 모든 운영 권한을 주면 최소 권한 원칙을 적용하기 어렵습니다. 반대로 너무 일찍 퍼미션을 도입하면 지금 규모에서 복잡도만 늘어납니다.

### 선택 가능한 옵션

- 옵션 A: 역할 기반만 유지한다
  - 장점: `USER`/`ADMIN` enum과 `RolesGuard` 하나로 인증 흐름이 끝나 추가 테이블·캐시·관리 화면 없이 구현과 검증이 가능합니다.
  - 단점: ADMIN 한 명이 모든 운영 기능에 접근할 수 있어 최소 권한 원칙을 적용할 수 없고, 운영자 유형(예: 콘텐츠 관리자 vs 사용자 관리자)이 늘면 역할만으로 세밀한 분리가 어렵습니다.

- 옵션 B: 역할은 묶음, 퍼미션은 실제 행위로 분리한다
  - 장점: 운영자 유형과 자원별 권한을 세밀하게 관리할 수 있습니다.
  - 단점: 정책 저장·캐시·관리 화면이 필요합니다.

### 추천안

지금은 역할 기반을 유지하되, 실제 ADMIN 엔드포인트를 만들 때 `@Roles(Role.ADMIN)`과 감사 로그를 함께 추가합니다. ADMIN 기능이 3개 이상의 독립된 행위 또는 운영자 유형으로 나뉘는 시점에 퍼미션을 도입합니다.

### 추천 이유

지금 ADMIN 라우트가 없으므로 퍼미션을 미리 구현할 실익은 낮지만 도입 기준은 지금 정해야 합니다.

### 영향 범위

- `backend/src/common/decorators/roles.decorator.ts`
- `backend/src/common/guards/roles.guard.ts`
- 향후 `admin` 모듈, Audit Log와 운영자 계정

### 추천 이유

지금 Service 중심 책임 분리를 유지하면서 타인 자원 접근을 코드 리뷰와 테스트에서 반복 검증할 수 있습니다.

# T4. 기존 Auth/User API 호환

## T4-01. 낡은 요청 약속의 폐기 정책

### 현재 상황

[코드에서 확인] `POST /recommendations/generate`는 `diagnosisId`가 있으면 서버 DB를 쓰고, 없으면 클라이언트가 보낸 `skinScore+weather`를 씁니다. `POST /products/weather-based`도 클라이언트 날씨 데이터를 Gemini 입력으로 씁니다. 기존 `/auth/login`은 User 필드와 토큰을 같이 반환합니다.

[미결정] 낡은 요청을 어느 기간 허용할지, 클라이언트가 보낸 데이터를 신뢰하는 방식의 종료 조건이 없습니다.

### 왜 결정이 필요한가

클라이언트 입력을 신뢰하면 사용자가 다른 피부·날씨 데이터를 추천 모델에 넣을 수 있고, 서버는 진단 근거를 재현할 수 없습니다. 호환 분기가 오래 남으면 최종 약속으로 넘어가지 못합니다.

### 선택 가능한 옵션

- 옵션 A: 두 형식을 계속 허용한다
  - 장점: 구버전 앱이 계속 동작합니다.
  - 단점: 보안·재현성·코드 복잡도 문제가 남습니다.

- 옵션 B: 앱 최소 버전과 종료일을 정해 diagnosisId 전용으로 전환한다
  - 장점: 서버가 소유권과 입력 근거를 통제합니다.
  - 단점: 모바일 강제 업데이트 또는 버전 분기 운영이 필요합니다.

### 추천안

옵션 B. `diagnosisId` 약속을 정식 약속으로 지정하고, 낡은 데이터는 폐기 로그와 지표를 남기는 한시적 호환으로만 유지합니다. `products/weather-based`도 인증 여부와 무관하게 서버가 WeatherService에서 최신 스냅샷을 확인하는 방향으로 확정합니다.

### 추천 이유

# T5. 날씨 모듈과 외부 API

## T5-01. 기본 지역 결정 기준

### 현재 상황

[코드에서 확인] 좌표가 없거나 측정소 조회가 실패하면 `KMA_AREA_NO`, `AIRKOREA_STATION_NAME` 환경변수 또는 `DEFAULT_REGION`을 씁니다. 좌표가 있을 때는 지역 목록과 실제 근접 측정소 조회를 조합합니다.

[미결정] 기본 지역을 환경변수로 운영할지, 버전 관리되는 지역 목록 또는 사용자 프로필을 기준으로 할지 확정되지 않았습니다.

### 왜 결정이 필요한가

기본 지역이 서버 환경에 묶이면 모든 사용자가 같은 지역을 볼 수 있고, 환경변수 변경이 데이터 재현성에 영향을 줍니다.

### 선택 가능한 옵션

- 옵션 A: 운영 환경변수로 기본 지역을 지정한다
  - 장점: 설정이 쉽고 장애 대비가 빠릅니다.
  - 단점: 지역 데이터와 설정 변경 이력이 분리됩니다.

- 옵션 B: 버전 관리되는 목록과 사용자 선택 지역을 쓴다
  - 장점: 코드·데이터로 재현 가능하고 사용자별 기본값을 지원합니다.
  - 단점: 지역 목록 관리와 사용자 설정이 필요합니다.

### 추천안

옵션 B. 목록을 정확한 area/station 매핑 기준으로 삼고, 환경변수는 초기 대비 또는 기본 region key만 지정합니다. 위치 권한 거부 시 사용자 선택 지역이 있으면 우선 쓰고 없을 때만 서비스 기본 지역을 씁니다.

### 추천 이유

지금 지역 목록과 환경변수가 모두 있는 과도기 구조를 명확히 정리할 수 있습니다.

## T5-02. 외부 API 타임아웃·재시도·서킷 브레이커 정책

### 현재 상황

[코드에서 확인] KMA, AirKorea, 근접 측정소 클라이언트 타임아웃은 각 8초, Gemini는 15초입니다. 타임아웃은 구현되어 있지만 명시적 재시도와 서킷 브레이커는 없습니다. 외부 API 실패는 해당 값 `null` 또는 Gemini 503으로 처리합니다.

[미결정] HTTP 상태별 재시도, 전체 요청 타임아웃 예산, 외부 API 연속 장애 차단 기준이 없습니다.

### 왜 결정이 필요한가

세 외부 날씨 호출이 순차로 지연되면 한 요청이 오래 연결을 점유할 수 있습니다. 무제한 재시도는 정부 API 장애를 악화하고, 재시도 안 하면 일시적 네트워크 오류를 모두 실패로 처리합니다.

### 선택 가능한 옵션

- 옵션 A: 지금 타임아웃만 유지하고 실패를 즉시 반영한다
  - 장점: 흐름이 단순하고 외부 장애를 증폭하지 않습니다.
  - 단점: 일시 장애 복구와 사용자 성공률이 낮습니다.

- 옵션 B: 제한적 재시도와 서킷 브레이커를 적용한다
  - 장점: 일시 오류를 흡수하고 지속 장애 시 빠르게 실패합니다.
  - 단점: 상태 관리·지표·튜닝이 필요합니다.

### 추천안

옵션 B. 타임아웃은 엔드포인트별로 유지하되 전체 `/weather`·AI 요청 예산을 별도로 둡니다. 연결 오류/5xx/429만 짧은 지수 백오프 + 지터로 1~2회 재시도하고 4xx·잘못된 응답은 재시도하지 않습니다. 연속 실패율·열림 시간·반열림 탐지 기준을 엔드포인트별로 문서화합니다.

### 추천 이유

외부 API를 보호하면서 일시적 네트워크 오류를 일부 흡수할 수 있습니다. 클라이언트가 분리되어 엔드포인트별 정책 적용이 쉽습니다.

### 영향 범위

- `backend/src/modules/weather/clients/**`
- `backend/src/modules/gemini/gemini.client.ts`
- `WeatherService`, `ProductService`, `RecommendationService`, 지표·알림 설정

## T5-03. 부분 실패와 날씨 스냅샷 품질 기준

### 현재 상황

[코드에서 확인] UV·오존·PM·CAI·NO2·SO2·CO는 각각 null일 수 있고, 하나 지표가 실패해도 다른 지표는 응답합니다. 모든 주요 지표가 null이면 `UNAVAILABLE`이고 진단은 날씨 스냅샷 없이 계속할 수 있습니다.

[미결정] 어떤 지표 조합이면 응답을 `LIVE`로 인정할지, 부분 데이터로 추천·패턴 분석을 수행할지 기준이 없습니다.

### 왜 결정이 필요한가

지금 "UV 또는 대기값 하나라도 있음" 기준은 "일부 값이 있음"과 "추천에 충분함"을 구분하지 않습니다. 품질이 낮은 스냅샷을 AI나 상관 분석에 쓰면 잘못된 결과가 나옵니다.

### 선택 가능한 옵션

- 옵션 A: 값 하나라도 있으면 LIVE로 취급한다
  - 장점: 데이터가 적어도 응답이 가능합니다.
  - 단점: 기능별 최소 품질이 보장되지 않습니다.

- 옵션 B: 목적별 충실도 기준을 둔다
  - 장점: 날씨 화면·추천·패턴이 필요한 데이터만 사용합니다.
  - 단점: 품질 기준과 상태 문서가 추가됩니다.

### 추천안

옵션 B. 날씨 화면은 필드별 null을 허용하고, 추천은 필수 입력이 부족하면 생성하지 않거나 근거 부족 상태를 반환하며, 패턴은 유효 쌍 기준으로만 계산합니다. source는 수집 출처이고 충실도는 별도 계산 필드 또는 서비스 정책으로 관리합니다.

### 추천 이유

화면 표시와 AI·통계 입력의 품질 요구가 다르므로 하나의 `LIVE` 값만으로 모두 판단하면 안 됩니다.

### 영향 범위

- `backend/src/modules/weather/**`
- `backend/src/modules/recommendations/**`
- `backend/src/modules/pattern/**`
- 날씨 DTO, EvidencePolicy와 프런트 상태 처리

# T6. 날씨 이력 저장

## T6-01. 날씨 스냅샷 보존·익명화·정리 정책

### 현재 상황

[코드에서 확인] 날씨 스냅샷은 지역명, 도시명, 위도/경도, 측정소, 관측·수집 시각과 지표를 영구 저장합니다. UNAVAILABLE 행은 저장하지 않지만 정상 스냅샷의 자동 정리 정책은 없습니다. 진단이 스냅샷 ID를 참조합니다.

[미결정] 날씨 이력의 보존 기간, 좌표 정밀도·익명화, 진단에 연결된 스냅샷의 보존 예외가 정해지지 않았습니다.

### 왜 결정이 필요한가

정밀 좌표는 개인 위치 정보가 될 수 있고, 스냅샷이 무한히 쌓이면 DB 비용이 증가합니다. 진단 재현에는 필요하지만 모든 원시 위치를 영구 보존할 필요는 없습니다.

### 선택 가능한 옵션

- 옵션 A: 모든 스냅샷을 장기 보존한다
  - 장점: 분석과 재현이 쉽습니다.
  - 단점: 개인정보와 저장 비용이 커집니다.

- 옵션 B: 기간·연결 여부에 따라 보존·익명화한다
  - 장점: 데이터 최소화와 재현성을 균형 있게 유지합니다.
  - 단점: 정리·익명화 job이 필요합니다.

### 추천안

옵션 B. 진단에 연결된 스냅샷은 진단 보존 기간 동안 지역 단위로 보존하고 정밀 좌표는 필요시 반올림 또는 제거합니다. 연결되지 않은 중복 스냅샷은 짧은 보존 기간 후 정리합니다. 보존 기간, 사용자 탈퇴 시 처리, 분석용 익명화 기준을 운영 정책으로 고정합니다.

### 추천 이유

지금 스냅샷은 개인 진단의 환경 근거이므로 무조건 삭제할 수는 있지만, 위치 데이터를 원시 그대로 무기한 저장할 이유도 없습니다.

### 영향 범위

- `backend/prisma/schema.prisma`
- `backend/src/modules/weather/weather.service.ts`
- `Diagnosis.weatherSnapshotId`, 정리/보존 job, 개인정보 정책

## T6-02. 날씨 스냅샷 중복 제거와 인덱스 정합성

### 현재 상황

[코드에서 확인] `WeatherService.persist()`는 지역명·kmaAreaNo·airkoreaStation·관측 분을 잠금과 `findFirst`로 중복 제거합니다. DB 인덱스는 `(regionName, observedAt)`이고 해당 조합의 유니크 제약은 없습니다. 좌표·수집 시각이 달라도 같은 관측 분이면 기존 행을 재사용합니다.

[미결정] 중복 제거 비즈니스 키를 DB 수준에서 보장할지, 서로 다른 출처·측정소·좌표를 어느 범위에서 같은 스냅샷으로 볼지 정해지지 않았습니다.

### 왜 결정이 필요한가

애플리케이션 잠금만으로는 다른 writer·마이그레이션 스크립트·운영 도구의 중복 저장을 막지 못합니다. 쿼리 조건과 인덱스가 어긋나면 중복 제거가 느려질 수 있습니다.

### 선택 가능한 옵션

- 옵션 A: 잠금 + findFirst를 유지한다
  - 장점: 지금 스키마 변경이 없습니다.
  - 단점: DB가 유일성을 보장하지 않습니다.

- 옵션 B: 정규화한 비즈니스 키/해시를 저장하고 유니크 인덱스를 추가한다
  - 장점: 모든 writer에 대해 중복을 방지합니다.
  - 단점: 기존 데이터 정리와 마이그레이션이 필요합니다.

### 추천안

옵션 B. 지역·area·station·관측 분·출처 맥락을 정규화한 중복 제거 키를 정의하고 유니크 인덱스 또는 별도 키 컬럼으로 보장합니다. 잠금은 동시 충돌 완화용으로 유지하되 데이터 정합성 최종 책임은 DB에 둡니다. 쿼리와 인덱스가 같은 필드를 쓰도록 `EXPLAIN`으로 검증합니다.

### 추천 이유

날씨 수집은 여러 요청·job·대비 경로에서 호출될 수 있으므로 DB 제약이 가장 안전합니다.

### 영향 범위

- `backend/src/modules/weather/weather.service.ts`
- `backend/prisma/schema.prisma`, 마이그레이션
- `backend/test/weather-persist.e2e-spec.ts`

## T7-02. RecommendationProduct 관계와 relatedProductIds 책임

### 선택 가능한 옵션

- 옵션 A: 관계 테이블을 유지하되 지금 API에서는 사용하지 않는다

## T8-03. Gemini 타임아웃과 AI 비동기 처리 기준

### 현재 상황

### 왜 결정이 필요한가

동기 AI 요청은 모바일 네트워크와 서버 worker를 오래 점유합니다. 비동기로 바꾸면 상태 조회·알림·재시도·중복 정책이 필요합니다.

### 선택 가능한 옵션

- 옵션 A: 모든 AI를 동기 처리한다
  - 장점: API와 프런트 흐름이 단순합니다.
  - 단점: 타임아웃과 worker 점유 문제가 있습니다.

- 옵션 B: 긴 작업은 큐 + 작업 상태로 처리한다
  - 장점: 재시도·확장·장시간 추론에 유리합니다.
  - 단점: Redis 큐/worker/상태 API를 운영해야 합니다.

### 추천안

지금 Gemini 추천은 동기를 유지하되 전체 요청 예산과 Rate Limit을 적용합니다. 이미지 추론 또는 p95가 합의한 임계값을 넘는 작업은 `PENDING → COMPLETED/FAILED` job으로 전환하고, Redis AI 작업 큐는 Python 제공자가 준비되는 별도 작업에서 도입합니다.

### 추천 이유

# T9. 진단 도메인 기반

## T9-01. InferenceProvider 운영 전환과 진단 상태

### 현재 상황

[코드에서 확인] `InferenceProvider` 인터페이스와 `MockInferenceProvider`가 있으며, 운영에서 모의는 실패 시 닫힘(fail-closed)됩니다. 실제 제공자가 없으면 진단 요청은 503입니다. 스키마에는 PENDING·COMPLETED·FAILED가 있지만 지금 제출 흐름은 성공 결과를 트랜잭션으로 저장하고 실패 상태 행을 일반적으로 저장하지 않습니다.

[미결정] Python 제공자 전환 시 동기·비동기 방식, 상태의 각 전이와 실패 결과 보존 여부가 정해지지 않았습니다.

### 왜 결정이 필요한가

진단이 오래 걸리거나 실패할 때 클라이언트가 무한 재시도하거나 중복 요청을 만들 수 있습니다. PENDING/FAILED enum이 실제 약속으로 쓰이지 않으면 모델의 의미가 불명확합니다.

### 선택 가능한 옵션

- 옵션 A: 추론 완료까지 동기로 처리하고 실패 행을 만들지 않는다
  - 장점: 지금 API와 DB 흐름이 단순합니다.
  - 단점: 장시간 작업·실패 이력·재처리가 어렵습니다.

- 옵션 B: 진단을 작업 상태로 관리한다
  - 장점: 상태 조회, 재시도, 운영 추적이 가능합니다.
  - 단점: 비동기 API와 worker가 필요합니다.

### 추천안

옵션 A를 지금 Gemini·모의 범위에서 유지하되, 실제 Python inference가 연결되거나 p95가 정한 기준을 넘으면 옵션 B로 전환합니다. 그때 `PENDING → COMPLETED/FAILED` 전이, 실패 사유의 외부 노출 여부, 재시도 횟수와 종료 상태를 명시합니다.

### 추천 이유

지금 작업 범위를 유지하면서 이미 스키마에 있는 상태 필드의 미래 의미를 명확히 할 수 있습니다.

### 영향 범위

- `backend/src/modules/diagnosis/**`

## T9-02. 이미지 업로드 메모리·동시성·검증 정책

### 현재 상황

[코드에서 확인] `FileFieldsInterceptor`는 메모리 저장을 쓰고 앞/좌/우 3개, 각 10MB, 파일 3, 파트 6으로 제한합니다. Service는 MIME·파일 시그니처·크기를 재검증하고 원본을 저장하지 않습니다. 전체 동시 업로드 수와 프로세스 메모리 예산은 없습니다.

[미결정] 동시 업로드 제한, 역방향 프록시 본문 제한, 이미지 변환·바이러스 검사, 요청 취소 시 버퍼 정리 기준이 없습니다.

### 왜 결정이 필요한가

요청당 최대 30MB까지 메모리에 적재될 수 있어 동시 요청이 많으면 메모리 부족(OOM)이 발생할 수 있습니다. MIME만 검사해도 악성·비정상 이미지가 inference 제공자로 전달될 수 있습니다.

### 선택 가능한 옵션

- 옵션 A: 지금 메모리 저장과 파일 검증만 유지한다
  - 장점: 디스크 I/O 없이 InferenceProvider에 버퍼를 바로 전달할 수 있어 구현이 단순합니다.
  - 단점: 요청당 최대 3×10MB=30MB가 프로세스 메모리에 적재되어 동시 사용자가 늘면 Node.js 힙 제한을 넘을 수 있고, MIME과 매직 바이트만 검사해 악의적 이미지나 대량 업로드 공격을 막기 어렵습니다.

- 옵션 B: 스트리밍/임시 객체 저장과 동시성·콘텐츠 검사 기준을 둔다
  - 장점: 메모리 사용을 제한하고 안전 검사를 확장할 수 있습니다.
  - 단점: 임시 파일 정리와 저장소 보안이 필요합니다.

### 추천안

옵션 B를 운영 트래픽 전에 적용합니다. 프록시·Nest·제공자의 최대 크기를 일치시키고 사용자·인스턴스별 동시 업로드 제한을 둡니다. 원본 영구 저장은 하지 않으며, 필요하면 암호화된 짧은 TTL 임시 저장소와 정리 job을 씁니다. 이미지 디코더 기반 콘텐츠 검사를 추가합니다.

### 추천 이유

지금 3 × 10MB 제한은 입력 검증일 뿐 전체 메모리 보호가 아닙니다. 진단 데이터의 민감도와 비용을 고려하면 동시성 예산이 필요합니다.

### 영향 범위

- `backend/src/modules/diagnosis/diagnosis.controller.ts`

## T9-03. 동의 기록과 개인정보 사용 목적

## T9-04. 진단 중복 제출과 멱원성 창

### 현재 상황

- 옵션 B: 클라이언트 멱원성 키와 이미지/요청 지문을 사용한다

### 추천 이유

## T10-01. 최소 진단 샘플 수 정책

### 현재 상황

[코드에서 확인] `PatternService`의 `MIN_SAMPLES`는 5이고, 그보다 적으면 404가 아니라 200 + `LOCKED`를 반환합니다. `requiredDays`와 `lockedMessage`에도 5가 반영됩니다. `BACKEND_TASKS.md`에 통계적 최소 일수 근거는 없습니다.

[미결정] 최소 기준을 5회로 확정할지 7·14·30회 등으로 바꿀지 정해지지 않았습니다.

### 왜 결정이 필요한가

표본이 적으면 상관계수가 크게 흔들리고 사용자가 우연한 관계를 의미 있는 패턴으로 오해할 수 있습니다. 프런트 문구와 API의 requiredDays도 함께 바뀝니다.

### 선택 가능한 옵션

- 옵션 A: 서로 다른 진단일 5일을 최소 기준으로 사용한다
  - 장점: 사용자가 짧은 기간 안에 READY 결과를 확인할 수 있고 지금 코드의 5회 기준과 가장 가깝습니다.
  - 단점: 표본 수가 작아 일시적인 날씨나 피부 상태가 상관계수에 크게 반영될 수 있습니다.

- 옵션 B: 서로 다른 진단일 7일을 최소 기준으로 사용한다
  - 장점: 일주일 단위의 생활·날씨 변화를 포함하면서도 사용자 대기 기간이 비교적 짧습니다.
  - 단점: 주간 특이 상황에 결과가 좌우될 수 있고 안정적인 개인 패턴으로 보기엔 여전히 표본이 적습니다.

- 옵션 C: 서로 다른 진단일 14일을 최소 기준으로 사용한다
  - 장점: 2주 동안의 변화를 반영해 5일·7일보다 우연한 상관관계를 줄일 수 있습니다.
  - 단점: 최소 2주 동안 꾸준히 진단해야 하므로 READY 전환율이 낮아질 수 있습니다.

- 옵션 D: 서로 다른 진단일 30일을 최소 기준으로 사용한다
  - 장점: 월간 환경 변화와 피부 변동을 가장 폭넓게 반영할 수 있습니다.
  - 단점: 사용자가 결과를 보기까지 너무 오래 걸리고 중도 이탈 가능성이 가장 높습니다.

### 추천안

옵션 C. 서로 다른 진단일 14일을 최소 기준으로 사용합니다. 지금 `diagnoses.length` 기준은 같은 날짜의 반복 진단을 여러 표본으로 계산하므로, 최종 결정 적용 시 서로 다른 날짜 기준으로 변경합니다.

### 추천 이유

지금 서비스는 하루 여러 번 진단할 수 있어 단순 회차는 실제 관찰 일수를 과대평가할 수 있습니다. 안정적인 패턴이라는 표현을 쓰려면 서로 다른 날짜 기준이 더 적절합니다.

## T10-02. C등급 추천 연결과 생성의 범위

## T10-03. 환경 지표 후보 범위와 결측 처리

### 현재 상황

[코드에서 확인] 분석 지표는 `uvIndex`, `pm25`, `pm10`, `ozonePpm`, `caiValue`이고 `no2`, `so2`, `co`는 제외되어 있습니다. 두 값이 모두 유효한 쌍만 계산하고 유효 쌍이 3개 미만이면 제외하며 `|r| < 0.1`도 제외합니다.

[미결정] NO2·SO2·CO의 분석 포함 여부와 쌍 단위 결측 처리·임계값을 나중에 바꿀 승인 기준이 없습니다.

### 왜 결정이 필요한가

날씨 스냅샷에는 더 많은 지표가 저장되므로 DB에 있는 값과 Pattern 결과의 범위가 달라질 수 있습니다. 결측 처리 변경은 상관 결과를 직접 바꿉니다.

### 선택 가능한 옵션

- 옵션 A: 지금 5개 지표와 쌍 기준을 유지한다
  - 장점: `uvIndex`·`pm25`·`pm10`·`ozonePpm`·`caiValue` 5개만 계산하므로 결과가 적고, 피부 직접 연관성이 낮은 지표의 노이즈가 사용자에게 노출되지 않습니다.
  - 단점: DB에 이미 저장된 `no2`·`so2`·`co` 값을 분석에 쓰지 않아 수집 비용 대비 활용도가 떨어지고, 피부-대기오염 추가 연관성을 검증하려면 패턴 정책 버전을 올려야 합니다.

- 옵션 B: NO2·SO2·CO를 포함하고 통계 기준을 재검증한다
  - 장점: 저장된 환경 데이터를 더 활용합니다.
  - 단점: 사용자 해석·노이즈·샘플 부족이 늘어날 수 있습니다.

### 추천안

옵션 A를 기본으로 유지합니다. 지표를 추가하려면 피부과학적 사용 목적, 최소 유효 쌍, 결측률, 다중 비교 문제를 검토하고 Pattern 정책 버전을 올립니다.

### 추천 이유

지금 저장 여부와 분석 대상은 다를 수 있으며, 지표를 많이 보여주는 것보다 오해를 줄이는 게 우선입니다.

# T11. 알림 설정 저장

## T11-01. 알림 기본값과 저장 시점

### 현재 상황

[코드에서 확인] NotificationPreference는 User와 1:1이며, 행이 없으면 DB에 쓰지 않고 기본값을 200으로 반환합니다. PUT은 전달된 필드만 갱신하고 행이 없으면 기본값과 함께 upsert합니다. pushEnabled 기본값은 false이고 실제 push/WebSocket/SSE 발송은 구현하지 않았습니다.

[미결정] 기본값의 제품 책임, 서버 기본값과 모바일 로컬 상태 충돌 시 우선순위, 최초 조회 시 행을 생성할지 정해지지 않았습니다.

### 왜 결정이 필요한가

설정 화면과 DB가 다른 값을 보이면 사용자가 알림을 끄거나 켜도 다음 실행에서 되돌아갈 수 있습니다. 발송 기능이 추가될 때 false/true의 의미도 달라질 수 있습니다.

### 선택 가능한 옵션

- 옵션 A: 지금처럼 GET은 계산값, PUT 때만 저장한다
  - 장점: 읽기에 부작용이 없고 행이 불필요하게 늘지 않습니다.
  - 단점: 기본값 변경이 기존 사용자에게 일관되게 적용되지 않습니다.

- 옵션 B: 가입 또는 최초 GET 때 기본 행을 생성한다
  - 장점: 사용자별 실제 설정이 항상 DB에 있습니다.
  - 단점: 읽기 요청이 쓰기가 되고 기본값 마이그레이션이 필요합니다.

### 추천안

옵션 A를 유지합니다. 서버 응답을 최종 기준(source of truth)으로 하고, 기본값 변경 시 명시적 마이그레이션 또는 버전 있는 기본값을 씁니다. push 발송을 시작하기 전 preference와 실제 알림 채널의 의미를 다시 확정합니다.

### 추천 이유

지금 Service 주석과 테스트가 읽기 부작용 없는 동작을 명확히 하고 있어 기존 설계가 합리적입니다.

### 영향 범위

- `backend/src/modules/notifications/**`
- `NotificationPreference`, 모바일 설정 동기화와 향후 push worker

## T11-02. 푸시 알림의 발송 주체와 preference 의미

### 현재 상황

[코드에서 확인] DB에는 `pushEnabled`, `uvAlertEnabled`, `dustAlertEnabled`, `morningReminder`가 있지만 발송 스케줄러·기기 토큰·알림 전달이 없습니다. T11 범위도 DB 저장만으로 제한되어 있습니다.

[미결정] 향후 알림을 NestJS 크론, 별도 worker, 외부 push 제공자 중 어디서 발송할지와 각 preference가 어떤 이벤트를 차단하는지 정해지지 않았습니다.

### 왜 결정이 필요한가

설정 필드가 있어도 발송 주체가 없으면 사용자가 기대하는 기능과 실제 동작이 다릅니다. 중복 발송·시간대·재시도·감사 기준도 필요합니다.

### 선택 가능한 옵션

- 옵션 A: NestJS가 동기 또는 크론으로 직접 발송한다
  - 장점: 구성 요소가 적습니다.
  - 단점: API 인스턴스 확장과 재시도에 취약합니다.

- 옵션 B: 이벤트/큐와 별도 알림 worker를 사용한다
  - 장점: 재시도·중복 방지·대량 발송에 유리합니다.
  - 단점: 큐·기기 토큰·운영 모니터링이 필요합니다.

### 추천안

옵션 B. Preference는 이벤트 유형별 opt-in/out으로 해석하고, 기기 토큰과 전달 상태를 별도 모델로 관리합니다. 같은 이벤트 ID의 중복 발송을 막고, KST 기준 발송 창과 실패 재시도 정책을 둡니다.

### 추천 이유

지금 알림은 저장만 하므로 실제 발송을 추가할 때 API Service에 외부 push 호출을 넣지 않고 독립적으로 확장할 수 있습니다.

### 영향 범위

# T12. Redis 날씨 캐시

## T12-01. 외부 API 장애 시 최근 DB 대비(fallback)

### 현재 상황

[코드에서 확인] Redis 미스 또는 Redis 장애 시 `WeatherService`는 외부 API를 직접 호출합니다. 외부 클라이언트가 실패하면 null 가능 지표와 `UNAVAILABLE`을 반환하며, 최근 날씨 스냅샷을 조회해 응답하는 경로는 없습니다. `getOrCreateSnapshot()`도 캐시를 쓰지 않습니다.

[미결정] Redis와 외부 API가 모두 실패할 때 같은 지역 최근 스냅샷을 반환할지 결정되지 않았습니다.

### 왜 결정이 필요한가

DB 대비는 가용성을 높이지만 오래된 날씨를 현재 값처럼 보여줄 위험이 있습니다. 패턴·추천 입력에 오래된 데이터가 들어가면 결과가 왜곡될 수 있습니다.

### 선택 가능한 옵션

- 옵션 A: DB 대비를 하지 않고 UNAVAILABLE을 반환한다
  - 장점: 최신성 없는 데이터를 명확히 거부합니다.
  - 단점: 외부 API 일시 장애에서 화면이 비게 됩니다.

- 옵션 B: 허용 연령 이내 최근 스냅샷을 대비로 반환한다
  - 장점: 사용자 화면 가용성이 높아집니다.
  - 단점: 오래된 상태·최대 연령·기능별 사용 제한을 관리해야 합니다.

### 추천안

옵션 B를 화면용 `GET /weather`에만 적용하고, 진단·추천 근거 스냅샷에는 기본 적용하지 않습니다. 대비 응답은 `STALE` 또는 명시적 `isStale` 상태를 쓰고, 허용 연령을 초과하면 `UNAVAILABLE`로 처리합니다.

### 추천 이유

화면 표시와 분석 근거의 최신성 요구가 다릅니다. 오래된 데이터를 LIVE/CACHED로 위장하지 않으면서 가용성을 확보할 수 있습니다.

### 영향 범위

- `backend/src/modules/weather/weather.service.ts`
- `WeatherSource` enum·DTO·Prisma 스키마/마이그레이션
- 날씨 화면, 진단/추천 입력 정책

## T12-02. DB 대비 출처 표시와 최대 허용 연령

### 현재 상황

[코드에서 확인] 지금 WeatherSource는 `LIVE`, `CACHED`, `UNAVAILABLE`뿐이며 DB 대비 출처는 구현되어 있지 않습니다. 최근 스냅샷 조회 시 `observedAt` 연령 조건도 없습니다.

[미결정] DB 대비를 선택할 경우 기존 CACHED를 재사용할지 새 STALE 상태를 도입할지, 얼마나 오래된 데이터를 허용할지 정하지 않았습니다.

### 왜 결정이 필요한가

캐시된 최신 응답과 DB의 오래된 관측값은 의미가 다릅니다. 구분하지 않으면 프런트가 오래된 데이터를 실시간 데이터로 표시할 수 있습니다.

### 선택 가능한 옵션

- 옵션 A: `CACHED`를 DB 대비에도 사용한다
  - 장점: enum·마이그레이션 변경이 없습니다.
  - 단점: Redis 캐시와 DB 오래된 값의 의미가 섞입니다.

- 옵션 B: `STALE`을 추가하고 최대 연령을 둔다
  - 장점: 출처와 최신성을 명확히 표현합니다.
  - 단점: 스키마·프런트·테스트 변경이 필요합니다.

### 추천안

옵션 B. `STALE`을 추가하고 기본 허용 연령은 제품·날씨 변동성 검토 후 정합니다. 추천 기준으로 재사용할 수 있는 연령과 화면 표시용 연령을 분리하며, 허용 범위를 넘으면 저장값을 사용하지 않습니다.

### 추천 이유

지금 출처가 이미 사용자에게 데이터 상태를 알려주는 약속이므로 오래된 값을 CACHED로 숨기는 건 약속 의미를 훼손합니다.

### 영향 범위

- `backend/src/common/enums/weather-source.enum.ts`
- `backend/prisma/schema.prisma`, 마이그레이션
- `backend/src/modules/weather/dto/weather-snapshot.dto.ts`, 프런트 상태 표시

## T12-03. 캐시 키 정밀도와 UNAVAILABLE 부정 캐시

### 현재 상황

[코드에서 확인] 좌표는 소수점 둘째 자리로 반올림해 `weather:current:{region}:{lat}:{lon}` 키로 만들고, 기본 지역은 별도 키를 씁니다. `LIVE`와 `UNAVAILABLE` 응답을 모두 기본 TTL 300초로 저장합니다. 캐시 히트 시 출처를 CACHED로 덮어씁니다.

[미결정] 좌표 묶음 크기, 지역·측정소 변경 시 키 무효화, UNAVAILABLE 부정 캐시 TTL을 별도로 둘지 정해지지 않았습니다.

### 왜 결정이 필요한가

좌표를 너무 넓게 묶으면 다른 관측소 값을 보여주고, 너무 좁게 묶으면 캐시 히트가 줄어듭니다. UNAVAILABLE을 오래 캐시하면 외부 API가 복구돼도 빈 데이터가 지속됩니다.

### 선택 가능한 옵션

- 옵션 A: 지금 2자리·모든 응답 300초를 유지한다
  - 장점: 캐시 키가 소수점 둘째 자리로 좌표를 묶고 TTL 300초를 쓰므로 지금 단위/통합 테스트와 e2e가 그대로 통과합니다.
  - 단점: 좌표 2자리 묶음은 약 1.1km 범위로 묶어 다른 측정소 결과를 같은 키로 캐시할 수 있고, `UNAVAILABLE`도 300초 동안 캐시되어 외부 API가 복구돼도 5분간 빈 데이터가 반환됩니다.

- 옵션 B: 위치 정밀도와 상태별 TTL을 분리한다
  - 장점: 정확도와 장애 복구를 독립적으로 조정합니다.
  - 단점: 키/TTL 정책과 테스트가 복잡해집니다.

### 추천안

옵션 B. 키는 실제 지역/측정소 정체를 우선하고 좌표 반올림은 해당 정체를 얻기 전 임시 묶음으로 사용합니다. LIVE와 UNAVAILABLE TTL을 분리하고, UNAVAILABLE은 짧은 부정 TTL을 씁니다. 좌표가 다른 요청을 같은 키로 합쳐도 허용 가능한 거리 기준을 문서화합니다.

### 추천 이유

날씨 API 장애 보호와 정상 복구 속도를 동시에 확보할 수 있습니다.

### 영향 범위

- `backend/src/modules/weather/weather-cache.ts`
- `backend/src/modules/weather/weather.service.ts`
- `RedisService`, 날씨 DTO와 캐시 계약 테스트

## T12-04. 캐시 몰림·무효화·지표 정책

### 현재 상황

[코드에서 확인] `RedisService.invalidate()`와 `invalidatePattern()`은 구현되어 있지만 WeatherService에서 정기 무효화 트리거는 없습니다. 같은 키 캐시 미스를 하나로 합치는 단일 비행/잠금은 없고, 히트율·지연·Redis 오류 지표도 없습니다. Redis 장애는 앱 부팅를 막지 않습니다.

[미결정] 무효화 시점, 수동 flush 엔드포인트 여부, 몰림 방지 방식, 캐시 지표와 알림 기준이 정해지지 않았습니다.

### 왜 결정이 필요한가

TTL만으로는 정부 API 갱신 시점과 맞지 않을 수 있고, 특정 지역 동시 요청이 외부 API를 한꺼번에 호출할 수 있습니다. Redis가 성능 계층이라도 장애와 히트율은 운영 판단에 필요합니다.

### 선택 가능한 옵션

- 옵션 A: TTL 만료와 수동 코드 호출만 사용한다
  - 장점: `RedisService.invalidate()`만 구현되어 있고 별도 스케줄러나 운영 엔드포인트가 없으므로 인프라 구성과 권한 관리가 최소화됩니다.
  - 단점: 정부 API 갱신 주기(분 단위)와 TTL 300초가 정렬되지 않아 최대 5분간 오래된 데이터가 반환될 수 있고, 같은 키에 동시 미스가 몰리면 여러 요청이 외부 API를 동시에 호출하는 캐시 몰림이 발생합니다.

- 옵션 B: 단일 비행, 주기 무효화, 지표·관리 엔드포인트를 도입한다
  - 장점: 외부 API 호출을 안정적으로 제어하고 상태를 관찰할 수 있습니다.
  - 단점: 스케줄러·운영 권한·지표 시스템이 필요합니다.

### 추천안

옵션 B. 캐시 미스에는 짧은 분산 잠금 또는 단일 비행을 쓰고, 정부 API 갱신 주기에 맞춘 키 무효화는 스케줄러가 담당합니다. 수동 flush는 ADMIN 전용 내부 운영 API로 제한합니다. 히트/미스, TTL, 채우기 지연, Redis 오류, 잠금 대기를 지표로 남깁니다.

### 추천 이유

지금 RedisService가 오류를 삼키는 구조이므로, 오류를 사용자 요청에 전파하지 않으면서 운영자가 성능 저하를 볼 수 있어야 합니다.

### 영향 범위

- `backend/src/redis/redis.service.ts`
- `backend/src/modules/weather/weather.service.ts`
- 스케줄러, ADMIN 운영 API, 지표·알림 시스템

# T13. 테스트와 API 계약

## T13-01. e2e 테스트 DB 격리 전략

### 현재 상황

[코드에서 확인] e2e는 공용 `todayskin_test` PostgreSQL을 쓰고 `test/jest-e2e.json`에서 `maxWorkers: 1`로 직렬 실행합니다. 각 파일이 before/after 훅에서 일부 데이터를 삭제합니다.

[미결정] 직렬 실행을 계속할지, 스키마·DB·트랜잭션 기반 격리로 병렬화할지 정해지지 않았습니다.

### 왜 결정이 필요한가

지금 방식은 경쟁을 줄이지만 테스트 시간이 늘고, 정리 누락이 다음 파일에 영향을 줄 수 있습니다.

### 선택 가능한 옵션

- 옵션 A: 공용 테스트 DB에서 `maxWorkers: 1`로 직렬 실행한다
  - 장점: 지금 설정과 테스트 정리 코드를 그대로 쓰며 경쟁을 가장 적은 변경으로 피할 수 있습니다.
  - 단점: 테스트 파일이 늘수록 CI 시간이 선형으로 증가하고 정리 누락이 다른 테스트에 영향을 줄 수 있습니다.

- 옵션 B: e2e 파일 또는 worker마다 PostgreSQL 스키마를 분리한다
  - 장점: 하나의 PostgreSQL 인스턴스에서 마이그레이션을 재사용하면서 테스트를 병렬 실행할 수 있습니다.
  - 단점: worker별 `DATABASE_URL`, 스키마 생성·삭제, 연결 풀 정리 로직이 필요합니다.

- 옵션 C: e2e 파일 또는 worker마다 독립된 테스트 DB를 사용한다
  - 장점: 스키마와 연결까지 완전히 분리되어 테스트 간 데이터 간섭 가능성이 가장 낮습니다.
  - 단점: DB 생성·마이그레이션 시간이 길고 로컬 Docker와 CI의 DB 관리가 복잡해집니다.

### 추천안

단기엔 옵션 A를 유지합니다. 테스트 수와 CI 시간이 임계값을 넘으면 옵션 B로 전환해 worker별 PostgreSQL 스키마를 생성하고 테스트 종료 후 삭제합니다. fixture는 고유 접두사와 사용자 범위를 씁니다.

### 추천 이유

지금 e2e가 공용 DB 정리에 의존하므로 즉시 병렬화를 강제하면 불안정 테스트가 생길 수 있습니다.

## T13-02. GeminiClient 모의 상태 확인 방식

### 현재 상황

[코드에서 확인] `GeminiClient`는 `isMockEnabled()` 공개 getter를 제공하고 T13 운영 모의 비활성화 e2e가 이를 씁니다. getter는 테스트와 운영 시작 로그 검증을 위해 노출되어 있습니다.

[미결정] 테스트 전용 상태 확인을 위해 공개 getter를 유지할지, 헬스/구성 진단 등 별도 검증 경로로 바꿀지 정해지지 않았습니다.

### 왜 결정이 필요한가

테스트 편의를 위한 공개 API가 제품 기능으로 굳어질 수 있습니다. 반대로 getter를 없애면 운영에서 모의 활성 여부를 확인하기 어렵습니다.

### 선택 가능한 옵션

- 옵션 A: 공개 getter를 유지한다
  - 장점: `prod-mock-disabled.e2e-spec.ts`가 `isMockEnabled()`로 운영에서 모의가 꺼져 있는지 직접 확인하므로 별도 진단 엔드포인트 없이 테스트와 운영 시작 검증이 가능합니다.
  - 단점: `GeminiClient` 공개 API에 모의 설정 노출 여부가 섞여 도메인 기능과 무관한 내부 상태가 API 표면에 남고, 다른 제공자에서도 유사 getter가 늘어날 수 있습니다.

- 옵션 B: 구성/헬스 진단으로 분리한다
  - 장점: 클라이언트 공개 API가 도메인 기능에 집중합니다.
  - 단점: 운영 진단 엔드포인트 보호와 테스트 설정이 필요합니다.

### 추천안

옵션 A를 지금 테스트 약속으로 유지하되 외부 HTTP API에는 노출하지 않습니다. 향후 준비/진단 응답에서 안전한 boolean과 제공자 모드를 제공할 때 getter를 내부 interface로 축소합니다.

### 추천 이유

지금 getter는 실제 운영 기능이 아니라 모의 실패 닫힘 검증용이며, 당장 제거하면 테스트 목적만 복잡해집니다.

### 영향 범위

- `backend/src/modules/gemini/gemini.client.ts`
- `backend/test/prod-mock-disabled.e2e-spec.ts`
- 헬스/준비 진단

### 추천 이유

## T13-04. 진단 → 날씨 → 패턴 READY e2e 범위

### 현재 상황

[코드에서 확인] 진단 e2e에서 외부 날씨 모의가 UNAVAILABLE이면 diagnosis의 `weatherSnapshotId`가 null이 됩니다. 패턴은 날씨 스냅샷이 연결된 진단만 쓰므로 지금 READY 흐름은 직접 스냅샷을 연결한 테스트와 단위 테스트에 의존하고, e2e는 LOCKED 중심입니다.

[미결정] 실제 사용자 흐름 전체를 READY e2e로 검증할지 정해지지 않았습니다.

### 왜 결정이 필요한가

단위 테스트만으로는 날씨 스냅샷 연결·인증·DB 쿼리·패턴 상태 전환의 통합 오류를 잡지 못합니다. 반대로 다수 진단 fixture는 e2e 실행을 느리게 합니다.

### 선택 가능한 옵션

- 옵션 A: LOCKED e2e와 READY 단위 테스트를 유지한다
  - 장점: `pattern.service.spec.ts` 단위 테스트가 외부 API 없이 빠르게 동작하고, `diagnosis-pattern.e2e-spec.ts`는 DB에 직접 스냅샷을 연결해 LOCKED 상태만 검증하므로 실행 시간이 짧습니다.
  - 단점: 실제 사용자 흐름인 진단 제출 → 날씨 스냅샷 연결 → 5개 이상 진단 → READY 상태 전환이 e2e로 검증되지 않아, WeatherService와 PatternService의 조인 오류나 상태 매핑 누락이 회귀로 발견될 수 있습니다.

- 옵션 B: 결정적 LIVE 날씨 스텁으로 READY e2e를 추가한다
  - 장점: 핵심 흐름을 실제 HTTP·DB로 검증합니다.
  - 단점: fixture와 실행 시간이 늘어납니다.

### 추천안

옵션 B를 핵심 smoke e2e로 최소 1개 추가합니다. 외부 정부 API가 아니라 테스트 제공자가 결정적 스냅샷을 반환하도록 하고, 최소 샘플·서로 다른 날짜·상관 결과·C등급 연결을 검증합니다.

### 추천 이유

외부 네트워크 없이도 T9→T6→T10의 실제 결합을 검증할 수 있습니다.

### 영향 범위

- `backend/test/diagnosis-pattern.e2e-spec.ts`
- 날씨 제공자 재정의, 진단/패턴/추천 fixture

## T13-05. ADMIN 엔드포인트 보호 테스트 대상

### 현재 상황

### 추천 이유

### 추천 이유

## T14-01. Prisma 마이그레이션 잠금과 기준선

### 현재 상황

  - 장점: 지금 package와 CI 흐름에 맞습니다.

- 옵션 B: 과거 잠금 형식을 함께 보존해 도구 호환을 시도한다
  - 장점: 기존 환경 일부와 호환될 수 있습니다.
  - 단점: 어떤 명령이 어느 파일을 읽는지 혼란과 어긋남이 생깁니다.

### 추천안

옵션 A. Prisma 7이 만든 단일 잠금 형식만 commit하고, 기존 테스트/개발 DB는 백업 후 스키마와 마이그레이션 diff를 검증한 뒤 기준선 기록을 등록합니다. `migrate dev`는 개발 전용, `migrate deploy`는 CI/운영 전용으로 구분합니다.

### 추천 이유

지금 CI가 마이그레이션 diff를 중요 품질 게이트로 쓰므로 잠금 파일과 기준선을 하나의 도구 기준으로 단순화해야 합니다.

### 영향 범위

- `backend/prisma/migrations/migration_lock.toml`
- `backend/prisma/migrations/**`

## T14-02. 운영 인프라·이미지·시크릿 주입·CD 방식

### 현재 상황

[코드에서 확인] Dockerfile, 로컬 PostgreSQL·Redis compose, GH Actions 빌드/테스트/린트/마이그레이션 diff가 있습니다. `docker/DEPLOYMENT.md`는 단일 서버 + docker compose를 권장하지만 ECS/Fly.io/Cloud Run/Kubernetes도 후보로 남기고, 자동 CD는 아직 없습니다. 운영 DB는 컨테이너 외부를 권장하며 시크릿은 컨테이너 외부 주입으로 설명합니다.

[미결정] 운영 서버, 이미지 registry, 시크릿 관리자, 관리형 DB, CD 자동 승인과 롤백 주체가 확정되지 않았습니다.

### 왜 결정이 필요한가

배포 자동화와 마이그레이션 실행 주체는 인프라에 따라 달라집니다. 확정 없이 CD를 만들면 시크릿·DB·롤백이 수동 문서와 실제 파이프라인에서 어긋납니다.

### 선택 가능한 옵션

- 옵션 A: 단일 VM/VPS에서 Docker Compose로 운영한다
  - 장점: 지금 Dockerfile·Compose·배포 문서를 거의 그대로 쓸 수 있고 초기 비용과 운영 복잡도가 낮습니다.
  - 단점: 단일 장애 지점이 생기며 자동 확장·무중단 교체 배포·자가 복구를 직접 구성해야 합니다.

- 옵션 B: Cloud Run·Fly.io 같은 관리형 컨테이너 플랫폼을 사용한다
  - 장점: 이미지 기반 배포, 헬스 체크, 자동 확장과 롤백을 플랫폼 기능으로 쓸 수 있습니다.
  - 단점: 플랫폼별 네트워크·콜드 스타트·비용 모델에 종속되고 장기 요청이나 고정 연결에 제약이 생길 수 있습니다.

- 옵션 C: AWS ECS 같은 관리형 컨테이너 오케스트레이션을 사용한다
  - 장점: VPC·관리형 DB·로드밸런서와 통합하면서 여러 인스턴스와 교체 배포를 안정적으로 운영할 수 있습니다.
  - 단점: IAM·네트워크·태스크 정의·배포 파이프라인의 초기 설정과 운영 비용이 증가합니다.

- 옵션 D: Kubernetes를 사용한다

## T14-03. 운영 마이그레이션 실행 주체와 다중 인스턴스 배포

### 왜 결정이 필요한가

  - 장점: 배포 절차가 단순합니다.
  - 단점: 다중 인스턴스와 롤백 제어가 어렵습니다.

- 옵션 B: 릴리스 단계에서 단일 마이그레이션 job을 먼저 실행한다

### 추천안

### 추천 이유

운영 DB를 애플리케이션 시작과 분리해야 다중 인스턴스와 무중단 배포를 안전하게 통제할 수 있습니다.

## T14-04. 활성·준비·헬스 체크 기준

### 현재 상황

[코드에서 확인] `GET /health`는 `{ status: 'ok', timestamp }`를 반환하는 프로세스 활성 엔드포인트입니다. DB·Redis 연결과 외부 API 준비를 확인하지 않으며 Docker HEALTHCHECK와 로드밸런서가 같은 엔드포인트를 씁니다.

[미결정] 활성과 준비를 분리할지, Redis·외부 API 장애를 시작/트래픽 준비에 반영할지 정해지지 않았습니다.

### 왜 결정이 필요한가

Redis는 선택적 캐시라 장애가 있어도 트래픽을 받을 수 있지만 DB는 핵심 의존성입니다. 하나의 헬스 엔드포인트에 모두 넣으면 일시적 외부 API 장애 때문에 인스턴스가 불필요하게 제거될 수 있습니다.

### 선택 가능한 옵션

- 옵션 A: 지금 `/health` 하나를 모든 검사에 사용한다
  - 장점: `GET /health`가 `{ status: 'ok', timestamp }`만 반환하므로 Dockerfile HEALTHCHECK와 로드밸런서가 하나의 엔드포인트로 동작하고 별도 검사 설정이 필요 없습니다.
  - 단점: DB 연결 실패·Redis 장애·외부 API 타임아웃이 모두 같은 200 응답으로 나와, DB가 죽어도 인스턴스가 살아있는 것으로 판단해 트래픽이 계속 유입되고, 반대로 Redis 일시 장애로 불필요하게 인스턴스가 제거될 수 있습니다.

- 옵션 B: `/health/live`와 `/health/ready`를 분리한다
  - 장점: 의존성별 중요도를 반영할 수 있습니다.
  - 단점: 검사·알림 설정이 추가됩니다.

### 추천안

옵션 B. 활성은 프로세스 이벤트 루프만 확인하고 준비는 DB·필수 구성·마이그레이션 상태를 확인합니다. Redis와 날씨/Gemini 외부 API는 선택적 또는 요청별 의존성으로 분리해 준비를 무조건 실패시키지 않습니다. 각 상태와 HTTP 코드를 문서화합니다.

### 추천 이유

지금 Redis가 선택적이고 외부 API가 부분 실패를 허용하므로 의존성을 한 엔드포인트에 묶는 건 서비스 설계와 맞지 않습니다.

### 영향 범위

- `backend/src/health/**`
- `backend/src/prisma/**`, `backend/src/redis/**`
- Dockerfile HEALTHCHECK, 로드밸런서·컨테이너 플랫폼 검사

## T14-05. 구조화 로깅·연관 ID·감사 로그

### 현재 상황

[코드에서 확인] Nest Logger로 부팅·Service·외부 API 오류를 기록하고 전역 예외 필터가 method·url·status·오류 이름을 로그로 남깁니다. 요청/연관 ID, JSON 구조, 전화번호·IP·좌표·토큰 마스킹, 로그 보관 기간, 사용자 행위 감사 로그는 없습니다.

[미결정] 운영 로그 필드·레벨·보관·민감정보 정책과 감사 대상이 정해지지 않았습니다.

### 왜 결정이 필요한가

장애 추적에는 한 요청이 인증→DB→외부 API로 이어지는 연결 정보가 필요합니다. 민감정보를 그대로 로그에 남기면 보안 사고가 됩니다. 일반 애플리케이션 로그와 법적 행위 기록도 목적이 다릅니다.

### 선택 가능한 옵션

- 옵션 A: 지금 문자열 Logger와 인프라 로그에 의존한다
  - 장점: Nest `Logger`로 문자열 로그를 stdout에 출력하므로 별도 로깅 라이브러리나 저장소 없이 인프라 표준 출력만으로 동작합니다.
  - 단점: `request.method + request.url` 형태라 한 요청이 인증 → DB → 외부 API로 이어지는 흐름을 연관 ID로 추적할 수 없고, 전화번호·IP·좌표가 마스킹되지 않은 채 로그에 남을 수 있으며, 로그 검색과 보관 기준이 없어 장애 원인 분석이 어렵습니다.

- 옵션 B: 구조화 로그와 별도 감사 로그를 도입한다
  - 장점: 요청 추적과 사용자 행위를 구분해 추적할 수 있습니다.
  - 단점: 스키마·보관·접근 권한을 운영해야 합니다.

### 추천안

옵션 B. 모든 요청에 서버 생성 연관 ID를 부여하고 method·라우트 템플릿·상태·소요시간·userId 해시·제공자·오류 코드를 JSON으로 기록합니다. 토큰·전화번호·생년월일·프롬프트 원문·이미지·정밀 좌표는 로그에서 제외하거나 마스킹합니다. 로그인·로그아웃·권한 변경·동의·진단 제출·데이터 삭제는 추가 전용 감사 로그 대상으로 삼습니다.

### 추천 이유

지금 예외 필터와 Service Logger가 이미 공통 지점이므로 미들웨어/인터셉터와 공통 로거를 추가해 단계적으로 통일할 수 있습니다.

### 영향 범위

- `backend/src/main.ts`
- `backend/src/common/filters/http-exception.filter.ts`
- 모든 Controller/Service, 감사 로그 스키마·로그 수집 시스템

## T14-07. 환경변수와 기능 플래그 수명주기

### 현재 상황

[코드에서 확인] Joi가 `NODE_ENV`, DB, Redis, JWT, 외부 API 키, 토큰 만료, `MOCK_GEMINI`, `MOCK_INFERENCE`를 검증합니다. 모르는 환경변수는 허용되고 테스트에서 DB/JWT 비밀키 빈 값이 허용됩니다. 기능 플래그는 운영에서 모의를 실패 닫힘하지만 소유자·만료·제거 규칙은 없습니다.

[미결정] 환경변수 소유권·시크릿 주입·변경 승인·환경별 필수값, 기능 플래그의 만료와 제거 기준이 없습니다.

### 왜 결정이 필요한가

잘못된 환경변수는 시작 이후에만 발견될 수 있고, 오래된 모의 플래그가 운영 동작을 바꿀 수 있습니다. 시크릿과 일반 설정은 보관·접근 정책이 달라야 합니다.

### 선택 가능한 옵션

- 옵션 A: `.env.example`와 Joi 검증만 유지한다
  - 장점: `env.validation.ts`의 Joi 스키마가 시작 시 필수 변수를 검증하므로 별도 registry나 시크릿 관리자 없이 `.env` 파일로 개발 환경을 구성할 수 있습니다.
  - 단점: `MOCK_GEMINI`·`MOCK_INFERENCE` 같은 기능 플래그에 소유자·만료일·제거 기준이 없어 운영에 실수로 남을 수 있고, 모르는 환경변수가 `allowUnknown: true`로 통과하므로 오타난 변수명이 조용히 무시될 수 있습니다.

- 옵션 B: 환경변수 registry와 기능 플래그 수명주기를 관리한다
  - 장점: 설정 책임과 운영 안전성을 명확히 합니다.
  - 단점: 문서·시크릿 관리자·CI 검증이 필요합니다.

### 추천안

옵션 B. 각 변수에 소유자·설명·필수 환경·안전 기본값·시크릿 여부를 기록하고 운영 시크릿은 Secret Manager에서 주입합니다. 모의 플래그는 테스트/개발 전용으로 제한하고, 소유자와 만료일이 없는 플래그는 merge를 거부합니다. 허용할 환경변수 목록과 모르는 키 처리도 운영에서 엄격하게 합니다.

### 추천 이유

지금 변수 종류와 검증이 이미 정리되어 있어 registry와 수명주기 필드를 추가하기 쉽습니다.

### 영향 범위

- `backend/src/config/env.validation.ts`
- `backend/.env.example`, `backend/docker/DEPLOYMENT.md`
- CI/CD, Secret Manager, `MOCK_GEMINI`, `MOCK_INFERENCE` 사용 코드

## T14-08. 의존성 감사·업데이트 정책

### 현재 상황

[코드에서 확인] 백엔드는 NestJS 11, Prisma 7, ioredis, proj4 등 외부 의존성을 쓰고 `package-lock.json`을 commit합니다. CI에는 빌드/테스트/린트/마이그레이션 검사가 있지만 의존성 감사와 정기 업데이트 게이트는 없습니다.

### 왜 결정이 필요한가

인증·DB·외부 HTTP 라이브러리 취약점은 서비스 전체 위험으로 이어집니다. 자동 주 버전 업데이트는 Prisma 마이그레이션이나 런타임 호환성을 깰 수 있습니다.

### 선택 가능한 옵션

- 옵션 A: 필요할 때 수동으로 의존성을 업데이트한다
  - 장점: 변경량과 위험이 작습니다.
  - 단점: 취약점 대응이 늦을 수 있습니다.

- 옵션 B: 감사와 정기 업데이트, 주 버전 업그레이드 검토를 CI/운영에 포함한다
  - 장점: 취약점을 지속적으로 발견하고 대응합니다.
  - 단점: 유지보수 시간을 정기적으로 확보해야 합니다.

### 추천안

옵션 B. PR에서 `npm audit` 또는 승인된 스캐너를 수행하고, critical/high 취약점에는 정해진 SLA를 둡니다. patch/minor는 정기 업데이트 창에서 자동 제안하되 빌드·단위·e2e·마이그레이션 diff를 통과시킵니다. Node·NestJS·Prisma 주 버전 업그레이드는 별도 마이그레이션/롤백 계획과 리뷰를 요구합니다.

### 추천 이유

지금 CI가 이미 백엔드 품질 게이트를 가지고 있어 의존성 검사를 추가하기 쉽고, Prisma 주 버전 변경은 DB 영향이 크므로 별도 기준이 필요합니다.
