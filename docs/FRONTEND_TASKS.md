- `main`에서 작업·커밋 금지. merge 후 브랜치 삭제 금지 (`--delete-branch` 금지).

### F65. 랜드마크 점이 화면에 보이지 않는다 (신규, 2026-08-13 실기기)

**백엔드는 정상이다.** 실기기 촬영분을 API로 직접 확인했다.

```text
GET /diagnosis/history/2026-08-13
  landmarks.points = 478개   image = 있음
  첫 점 = [0.5039, 0.6176]   ← 0~1 정규화 좌표
```

DB에도 478점이 저장돼 있고 이미지 row도 살아 있다. 즉 저장 동의·추론·노출 조건은 모두 통과했고
남은 것은 **렌더링**이다. 오버레이는 `app/(tabs)/history.tsx`(`MediaThumb`)와
`app/diagnosis/[id].tsx`에 이미 있고 `react-native-svg`도 설치돼 있다. 유력한 원인 두 가지다.

1. **점이 너무 작다.** `viewBox="0 0 1 1"`에 `r={0.01}`(썸네일) / `r={0.008}`(상세)이다. 140×160 박스로 환산하면 반지름이 1.5px 안팎이고, 반투명 세이지색이라 사진 위에서 사실상 안 보인다. 점 크기를 픽셀 기준으로 잡거나 뷰박스를 픽셀 좌표계로 바꿔야 한다.
2. **이미지와 오버레이의 종횡비가 어긋난다.** 이미지는 `resizeMode="cover"`로 잘라 채우는데 SVG는 `preserveAspectRatio="none"`으로 늘려 채운다. 두 좌표계가 달라 점이 얼굴에서 밀린다. 이미지를 `contain`으로 맞추거나 실제 이미지 비율을 재서 오버레이에 같은 비율을 적용해야 한다.

- [ ] 실기기에서 점이 "안 보이는" 것인지 "엉뚱한 곳에 찍히는" 것인지 먼저 눈으로 확인한다. 위 두 원인은 증상이 다르다
- [ ] 점 반지름을 화면 픽셀 기준으로 잡는다. 뷰박스 스케일에 딸려 축소되지 않게 한다
- [ ] 이미지와 오버레이가 같은 좌표계를 쓰게 맞춘다. 얼굴 위 점이 코·눈 위치와 맞는지 확인한다
- [ ] 478점을 다 그리는 게 성능·가독성 면에서 맞는지 판단한다. 윤곽선만 잇거나 부위별로 솎는 편이 읽기 쉬울 수 있다 (F3 랜드마크 UI와 같은 결정)
- [ ] 랜드마크 렌더링에 테스트가 없다. 정규화 좌표 → 화면 좌표 환산 함수를 분리해 단위 테스트로 고정한다

완료 기준: 실기기 기록 화면에서 촬영한 얼굴 위에 랜드마크가 제 위치에 보이고, 좌표 환산이 테스트로 고정된다.

검토 과정에서 시각을 남기는 안(`2026.08.13 03:41`)도 제시했다. 이 문구가 붙은 카드가
"촬영 당시 날씨"를 설명하는 자리라 시각이 없으면 어느 시점 날씨인지 알 수 없어지고,
자외선은 시간대별로 크게 달라 특히 그렇다. 그럼에도 화면을 간결하게 두는 쪽을 택했다.

따라서 **하루에 두 번 이상 촬영한 경우 카드만 보고 구별할 수 없다**는 점을 감수한다.
하루 1건이 일반적이라는 전제에 기댄 결정이므로, 다회 촬영이 늘면 재검토한다.

- [ ] `formatCapturedAt`을 `YYYY.MM.DD`로 바꾼다. 0을 채워 자리수를 고정해야 목록에서 세로 정렬이 맞는다. 시각을 안 쓰게 되므로 함수명도 맞게 바꾼다
- [ ] `촬영` 접미사를 유지할지 정한다. 날짜만 남으면 `2026.08.13 촬영`이 자연스러운데, 카드 맥락상 접미사 없이 날짜만 두는 편이 더 깔끔할 수 있다
- [ ] 날짜 표기 함수를 `src/lib/kst-date.ts`로 옮긴다. 지금 화면 파일 안에 있어 다른 화면과 표기가 갈라질 수 있다. 기존 `formatDateKo`('8월 1일')와 함께 쓰임새를 정리한다
- [ ] 캘린더·추이 화면의 `formatDateKo` 표기도 같이 바꿀지 정한다. 캘린더는 맥락상 월·일만으로 충분해 그대로 두는 편이 나을 수 있다
- [ ] `formatCapturedAt`은 UTC 게터로 KST를 읽는 올바른 방식을 쓰고 있다(백엔드 N39의 실수와 대비). 옮길 때 이 방식을 깨지 않는다
- [ ] 날짜 경계(자정 전후) 케이스를 단위 테스트로 고정한다

완료 기준: 기록 화면의 촬영 시각이 숫자 표기로 통일되고, 표기 함수가 한 곳에 모여 테스트로 고정된다.

### F64. 지표별 등급 라벨 분리 (완료)

브랜치: `feature/indicator-grade-vocabulary` (백엔드 N40과 같은 PR)

자외선·오존·미세먼지·초미세먼지·통합지수가 전부 같은 어휘(좋음/보통/나쁨)를 썼다.
실기기에서 자외선지수 9가 "나쁨"으로 표기됐는데 기상청 기준으로는 "매우높음"이다.

- [x] `src/lib/air-status.ts`를 지표별로 나눈다 — `AIR_STATUS_*`(4단계) / `UV_LEVEL_*`(5단계). `Record`로 선언해 등급이 늘면 컴파일이 실패하는 성질은 유지
- [x] 색상 단계를 등급 수에 맞춰 늘린다 — 기상청 관례(낮음 녹 · 보통 황 · 높음 주황 · 매우높음 적 · 위험 보라)에 맞춰 주황·보라를 추가하고, 대기질 '매우나쁨'용 진한 적색을 추가
- [x] `weather-detail.tsx`의 게이지 눈금을 지표별 어휘로 바꾼다 — 하드코딩된 `['좋음','보통','나쁨']`을 제거하고 등급 순서 배열(`*_ORDER`)에서 뽑는다
- [x] 홈 카드·상세·기록의 어휘 일치 확인 — `StatusBadge`·`WeatherMetric`·기록 그리드까지 스케일을 판별 유니온으로 받게 바꿔, 지표에 맞지 않는 등급을 넘기면 컴파일이 실패한다

**타입을 갈랐더니 숨어 있던 문제 둘이 드러났다.**

프론트 등급 타입이 손으로 적혀 있어(`AirStatus = 'good'|'moderate'|'bad'`) 서버가 등급을
늘려도 드리프트 검사를 그대로 통과했다. 생성 타입에서 파생하도록 바꿨다.

`status === 'bad'` 비교가 새 등급을 놓쳤다. '매우나쁨'일 때 미세먼지·오존 경고 문구가
사라진다. 컴파일러가 잡을 수 없는 종류라 `isAirConcerning()`으로 묶었다.

완료 기준: 자외선은 낮음~위험, 대기질은 좋음~매우나쁨으로 표기되고, 세 화면의 어휘가 일치한다. → 충족
